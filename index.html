01 — Same CSP re-assigned in single-CSP zones (P51 cooldown bypass)

BUG
Impl miss
The OS says NO, the code says YES. In single-CSP zones the DAS routing engine deliberately bypasses the P51 cooldown and re-routes a failed-install booking back to the same CSP — sometimes within seconds.

Two coupled fixes must ship together:
(1) Remove the SINGLE_CSP_ZONE_CONTINUITY bypass in the routing engine.
(2) Wire the missing incrementAssignmentCount call on DAS's install-failure path (InboundEventProcessingServiceImpl.handleClStateChanged) so the P195 ping-pong counter advances. Today it doesn't — counter sits at {} on every allocation row in prod. OS L572 explicitly says P195 covers "…or fail the same connection"; the code violates this. The P195 value itself is read from AWS Parameter Store at runtime — not hardcoded in DAS — so this fix is pure plumbing.

Either fix in isolation leaves a loop open. Together: each CSP can be re-assigned the same connection up to the P195 cap, with a 4-hour gap (P51), then permanently excluded.

Spec — handed to tech

Today

  • When a CSP marks installation failed, the system correctly applies a 4-hour cooldown for that CSP on that connection.
  • The routing engine correctly excludes cooldowned CSPs from re-selection — except in zones with only one eligible CSP, where the SINGLE_CSP_ZONE_CONTINUITY bypass silently re-includes the cooled-down CSP and sends the booking right back to the same partner (sometimes within seconds).
  • The P195 ping-pong counter that should cap "how many times the same CSP gets the same booking" silently doesn't increment on the install-failure path. So even outside the single-CSP-zone bypass, the system has no protection against a CSP being re-tried beyond the P195 cap. In prod today, assignment_count_per_csp = {} on every allocation row — the counter literally never advances.
  • Net effect: a CSP can rapid-reject install-failures and have the booking come right back. The loop is bounded only by CL P78 = 3 (terminal at the 4th install-failure event), typically within minutes.

Want

  • When a CSP marks installation failed, the 4-hour cooldown applies absolutely — including in zones where only one CSP is eligible. No exceptions.
  • The P195 ping-pong cap applies absolutely on install-failure: once a CSP hits the P195 cap on a given connection, that CSP is permanently excluded from this connection's routing pool. The OS sanctions this in L572 — "Prevents infinite ping-pong when limited CSPs repeatedly decline or fail the same connection." Combined with P51, each CSP gets up to the P195 cap's worth of attempts per connection-lifetime, with a 4-hour gap between them. The cap's exact value is read from AWS Parameter Store; tech does not hardcode it.
  • If no other CSP is eligible (during the cooldown window, or after P195 exhaustion), the booking stays unallocated. The customer waits. This is consistent with OS L540 ("service vacuum accepted") — the OS expects Capacity OS to address the supply problem, not for DAS to paper over it.

Edge cases (well-scoped, business only)

  1. Zone has 2 or more eligible CSPs, one is cooldowned. Routing picks one of the others. (No change from today's correct behaviour.)
  2. Zone has only one eligible CSP, and that CSP just failed install. Booking stays unallocated for 4 hours. The customer is not assigned a new partner during the cooldown — intentional per OS.
  3. After 4 hours the cooldown expires (single-CSP zone, P195 count below cap). The CSP becomes eligible again; routing may re-select them. A subsequent install-failure applies a fresh 4-hour cooldown and bumps the P195 count.
  4. Once the P195 cap is reached. P195 excludes the CSP permanently from this connection's routing pool. In a single-CSP zone, routing engine finds no eligible CSPs → ALLOC_STATE_ROUTING_FAILURE emitted → connection stays UNASSIGNED → CL P75 (7d) eventually deactivates. In a multi-CSP zone, the routing engine picks a different CSP.
  5. CSP fails install on multiple connections in the same zone. Each connection has its own independent cooldown and P195 counter — both are scoped per (CSP, connection), not per CSP.
  6. D&A's own routing retries (P50) exhaust while the cooldown is still active. The connection moves to ROUTING_FAILURE via the existing path. No new behaviour from this fix.

Out of scope

  • Customer notification that their booking is on hold during the cooldown. Not in this item.
  • CSP notification that they declined and are on cooldown (no PN to the CSP). Not in this item.
  • Exit OS S4 escalation behaviour on routing failure. Exit OS is not implemented today; separate matter, not a dependency for this fix.

Risks / dependencies

  • Both fixes must ship together. Removing the bypass alone leaves the rapid-reject vector partially open (CSP fails install, waits out 4h cooldown, gets re-selected, fails again — bounded only by CL P78 = 3). Wiring P195 alone is overridden by the bypass (which re-includes the cooled-down CSP regardless of the P195 predicate). Together: the P195 cap (value per AWS Parameter Store) actually bounds per-CSP attempts, with a 4h gap between them — the OS-intended behaviour at OS L572.
  • Customer impact data. In the last 14 days, 27 of 39 connections (69%) that hit the SINGLE_CSP_ZONE_CONTINUITY bypass ended retry-exhausted (PENDING_DEACTIVATION with retry_exhausted=true). Median gap between consecutive install-failures: 34 seconds. Minimum: 7 seconds. The bypass + missing P195 combo is actively killing bookings.
  • Single-CSP zones will see longer customer waits (visibly). Once both fixes ship, low-supply zones where the lone CSP refuses installs will have bookings sit UNASSIGNED after the second install-failure rather than thrashing for ~3 minutes until P78 kills them. This is the OS-mandated behaviour (L540 — "service vacuum accepted") but it is a visible product change. The OS expects Capacity OS to resolve the supply problem, not DAS to paper over it.
  • No schema change. V17__cooldown_audit_columns.sql (cooldown_bypassed, cooldown_bypass_reason) can stay — they'll be false / null after the fix. The assignment_count_per_csp column is already in place; the fix just starts populating it.
  • Test fallout. Search RoutingEngineServiceImplTest and friends for cooldownBypass / SINGLE_CSP_ZONE_CONTINUITY — those tests assert the buggy behaviour and must be updated/removed. Also add tests that verify assignment_count_per_csp advances on every handleClStateChanged call with entry_reason=RETRY.

Spec — handed to tech

Today

  • The customer backend routes both customer-initiated and system-initiated cancellations through the same path — a POST to CL's /events/user-cancellation endpoint.
  • CL correctly records the cancellation reason on the connection and emits CL_DEACTIVATION_INITIATED with the reason in the payload — but TAS's deserialized record drops the reason field.
  • TAS's handler hard-codes reason="DEACTIVATION" and always calls cancelByUpstream(...). Every cancellation lands in CANCELLED_BY_UPSTREAM.
  • The CANCELLED_BY_CUSTOMER terminal exists in the spec and state machine but is never reached in production (zero rows in the database, ever). The customer-cancel branch is effectively dead code.

Want

  • Customer backend: stop lumping system-cancels into the customer-cancel signal. Either use distinct endpoints / events for customer-initiated vs system-initiated, or carry a cause flag the install side can read. (Bifurcation mechanism: tech's call.)
  • TAS: stop dropping the cause. Extend the inbound ClDeactivationInitiated record to keep the deactivation_reason (and ideally actor_type) that CL is already emitting. Update the handler to branch:
    • deactivation_reason = USER_CANCELLATION → cancelByCustomer(...) → CANCELLED_BY_CUSTOMER.
    • Anything else → cancelByUpstream(...) → CANCELLED_BY_UPSTREAM (with the reason carried through to reason_code).
  • No new terminal states. No state-machine changes. Existing transitions already cover both branches.
  • No PN / partner-app / customer-app change in this item — bifurcated data simply becomes available for future PN work to consume.

The exhaustive list of scenarios that qualify as "system-initiated" is owned by — and already defined in — the customer backend. This spec only requires that whichever scenarios the customer backend already classifies as system-initiated route to CANCELLED_BY_UPSTREAM on the install side; the customer-initiated path continues to land in CANCELLED_BY_CUSTOMER.

Edge cases (business)

  1. Customer cancels via the customer app. Lands in CANCELLED_BY_CUSTOMER. (NEW outcome — today this incorrectly lands in CANCELLED_BY_UPSTREAM because TAS drops the cause field.)
  2. Booking auto-expires / stuck-at-stage / all-CSPs-declined. Customer backend's watchdog cancels. Lands in CANCELLED_BY_UPSTREAM with a system-cause reason_code (auto-expiry / stage-stagnation / supply-exhausted / etc., as the customer backend already classifies it). (NEW reason granularity — today they also land in CANCELLED_BY_UPSTREAM but with the same generic DEACTIVATION reason as customer cancels.)
  3. CSP-side cancel paths (CL T11/T12 retry-exhaustion, D&A REALLOCATION_PENDING, Exit OS, Enforcement) continue to land in CANCELLED_BY_UPSTREAM as today. No change to those.
  4. Cancellation signal arrives without a recognisable cause (malformed payload / unexpected source). Reject / log; do not default to CANCELLED_BY_CUSTOMER (and do not default to CANCELLED_BY_UPSTREAM silently either — the fix is to make the cause explicit, not to pick a fallback).

13 — CLOS P74 (72h) + DAS P41 (2h): does the timer start from ASSIGNED or from ACCEPTED?

DECISIONPending on Dhruv
Two of the timer sweeps in Items 03 and 05 (CLOS P74 install window + DAS P41 acceptance window) need a product decision before they can be safely wired in prod: when does the clock start? From the moment the candidate enters the ASSIGNED state (per the OS state diagram), or from the moment the CSP accepts the allocation (the ACCEPTED state)? The answer changes who gets penalised when there's wiring latency, and it changes the effective length of the customer-facing install window.
LayerStatusNotes
OS (CL + DAS)⚠ AmbiguousCL OS L572 (P74 = 72h install window) and DAS OS (P41 = 2h acceptance window) define the durations but don't explicitly fix the start anchor across both interpretations. Reasonable readings exist for both ASSIGNED and ACCEPTED.
Items 03 + 05✗ Carved outItems 03 (CLOS scheduler) and 05 (DAS scheduler) explicitly exclude P74 and P41 respectively. They wire P75/P76/P77/P78 and P191 only, until this decision lands.
Prod impact⚠ DownstreamOnce Dhruv decides, Items 03 and 05 absorb the answer and become unblocked. Anchor choice also affects the TAS T3-retry co-fix semantics under Item 03.

The two options

OptionStart anchorWhat it means for P74 (72h install window)What it means for P41 (2h acceptance window)
Option A ASSIGNED entry Customer's 72h clock starts the moment DAS picks the CSP, even if the CSP hasn't acknowledged. Wiring delays / push-notification slowness eat into the customer's window. 2h cap measured from DAS's pick. Acceptance signal must reach DAS within 2h of the candidate row being written.
Option B ACCEPTED entry 72h clock starts when the CSP accepts. Customer gets the full 72h of CSP-engaged install time, regardless of pre-accept latency. 2h cap measured from when the CSP acknowledges (or auto-accept fires). Pre-accept wait doesn't count.

What each option changes downstream

  • Item 03 (CLOS scheduler): P74 sweep query joins on the start-anchor column. Option A: WHERE assigned_at < now() - 72h. Option B: WHERE accepted_at < now() - 72h. TAS T3-retry handling follows the same anchor.
  • Item 04 (DAS scheduler): P41 sweep query similarly. Option A: WHERE assigned_at < now() - 2h AND state = 'ASSIGNED'. Option B: WHERE accepted_at < now() - 2h (which makes P41 effectively redundant if auto-accept is fast).
  • Customer-facing install-window guarantees: Option A gives a worst-case shorter window if there's pre-accept latency; Option B gives a stable 72h guarantee regardless of wiring lag.
  • CSP penalty surface: Option A penalises CSPs (and Wiom) for system-side latency; Option B penalises only post-accept inactivity.

What this item asks

PM decision required from Dhruv: for both P74 (CL install window, 72h) and P41 (DAS acceptance window, 2h), is the start anchor ASSIGNED entry (Option A) or ACCEPTED entry (Option B)? Same answer applies to both timers, or do they need separate anchors?

Items 03 and 05 cannot ship the P74 / P41 portions until this is locked. The rest of those items (P75/P76/P77/P78 in CLOS, P191 in DAS) is independent of this decision and proceeds under Bucket 1.
