Installation Flow — Tech Handover · BUG-04

DAS skips active-connection increment — P46 routing enforcement effectively disabled

DAS routing's per-CSP-per-zone P46 cap guard (AllocationGuards.guardCspBelowP46Cap) reads CspZoneExposureEntity.activeConnections — but this counter is only ever decremented, never incremented in DAS code. The counter stays clamped at 0 → the guard if (activeConnections >= p46CapacityCap) never trips → P46 cap enforcement at routing time is effectively disabled. DAS will allocate to a CSP regardless of their actual active load. Real-time, every allocation, every zone. Not CSP-app-visible — partner app reads CL directly.

Owner: Ashish Raj
Date: 2026-06-04
Bug

Original spec

Source: os/Demand_Allocation_OS_v1_9_1_LOCKED.md · §4.2 (L205): "Load Ratio (for routing) = Active connections / P46 capacity cap. Used in §4.3 Stage 5 utilization ranking." §4.2 (L203): "Zone Share = Active connections served by CSP / Total active connections in zone." §4.3 Stage 3 Gate 3e: P46 cap enforcement at allocation time (guardCspBelowP46Cap).
Active-connection semantics (per CL OS): a connection is "active" only while its CL state = ACTIVE. Excludes REQUESTED, PENDING_INSTALL, PAUSED, PENDING_DEACTIVATION, DEACTIVATED.
CL events DAS subscribes to today: CL_CONNECTION_ACTIVATED (carries activation_source ∈ {INITIAL, RESUME, RENEWAL}), CL_DEACTIVATION_INITIATED (carries previous_state), CL_CONNECTION_DEACTIVATED, CL_STATE_CHANGED.

Workflow — how CspZoneExposureEntity.activeConnections is supposed to move

DAS routing's P46 cap guard reads a per-CSP-per-zone counter (CspZoneExposureEntity.activeConnections). DAS subscribes directly to CL events and derives this counter from CL state transitions. The diagram below shows the intended behaviour and where the bug bites.

stateDiagram-v2 [*] --> REQUESTED : CONNECTION_REQUEST REQUESTED --> PENDING_INSTALL : T1 ALLOCATION_ACCEPTED PENDING_INSTALL --> ACTIVE : T2 INITIAL — DAS counter +1 ACTIVE --> ACTIVE : RENEWAL — DAS counter no-op ACTIVE --> PAUSED : T4 — DAS counter -1 PAUSED --> ACTIVE : RESUME — DAS counter +1 ACTIVE --> PENDING_DEACTIVATION : T5 or T6 — DAS counter -1 PAUSED --> PENDING_DEACTIVATION : T7 P76 sweep — DAS counter no-op PENDING_DEACTIVATION --> DEACTIVATED : T8 P77 finalised DEACTIVATED --> [*]

Per-event behaviour — today vs intended (DAS-side)

CL emits CL_CONNECTION_ACTIVATED with three distinct activation_source values. The fix must discriminate carefully — fixing INITIAL while leaving RENEWAL untouched.

CL eventsource / previous_stateState transitionToday (DAS code)Intended (per CL state semantics)
CL_CONNECTION_ACTIVATED INITIAL PENDING_INSTALL → ACTIVE no-op (handler exists, doesn't touch counter) +1
CL_CONNECTION_ACTIVATED RESUME PAUSED → ACTIVE no-op +1
CL_CONNECTION_ACTIVATED RENEWAL ACTIVE → ACTIVE no-op no-op (must stay — naïve "always +1" would over-count)
CL_CONNECTION_PAUSED n/a ACTIVE → PAUSED no handler (DAS doesn't subscribe) −1
CL_DEACTIVATION_INITIATED previous_state = ACTIVE ACTIVE → PENDING_DEACTIVATION state-tracking only (line 284), no counter change −1
CL_DEACTIVATION_INITIATED previous_state = PAUSED PAUSED → PENDING_DEACTIVATION state-tracking only, no counter change no-op
CL_CONNECTION_DEACTIVATED (terminal, post-P77) PENDING_DEACTIVATION → DEACTIVATED −1 at line 350 (only mutation site in all of DAS) no-op (already decremented at PAUSE or DEACT_INITIATED)

Where the counter is used downstream (inside DAS)

  • P46 routing guard — AllocationGuards.guardCspBelowP46Cap() line 78: if (exposure.getActiveConnections() >= exposure.getP46CapacityCap()) throw CSP_AT_CAPACITY_CAP. This is the routing-time enforcement that's effectively disabled today.
  • Continuity-cap guard — guardCspBelowContinuityCap() line 89: same read, compared against P46 cap × continuity ratio.
  • Routing telemetry — RoutingEngineServiceImpl:480-482 emits {active, p46, load} on every allocation decision. Today's load is always 0 in production logs.

Where the bug bites — and the fix shape

Net effect today: the counter is the wrong number — clamped at 0 from a never-incremented baseline → routing's P46 guard never trips → DAS over-allocates per CSP, every zone. Real-time impact at allocation time.

Fix shape — three coordinated changes:

  1. Add INCREMENT in handleClConnectionActivated (current line 305-321). Allowlist INITIAL and RESUME: if ("INITIAL".equals(source) || "RESUME".equals(source)) { ... setActiveConnections(current + 1) ... }. Do NOT add an unguarded increment — that would also fire on every RENEWAL (recharge of an already-ACTIVE connection) and over-count across each connection's lifetime.
  2. Add new handleClConnectionPaused handler + corresponding inbound endpoint POST /cl-connection-paused + CL outbox subscription. Decrement on every ACTIVE → PAUSED transition.
  3. Move the decrement from handleClConnectionDeactivated (current line 350, fires on terminal CL_CONNECTION_DEACTIVATED) to handleClDeactivationInitiated (current line 284). Gate on previous_state = ACTIVE only. Terminal CL_CONNECTION_DEACTIVATED becomes a no-op for this counter — the connection's exit from ACTIVE was already accounted for at PAUSE or at DEACT_INITIATED, so a terminal decrement would double-count.

The three together produce a counter that strictly matches "currently in ACTIVE state per CL OS." P46 routing enforcement comes back on and tracks reality across the connection's full lifecycle, including pauses. Without change #3, the existing line-350 decrement causes double-counting on the PAUSE → PENDING_DEACT → DEACTIVATED path — the three changes are coupled.

What this fix does NOT depend on

  • No cross-service coordination required. Verified: zero HTTP clients from DAS to other services for this counter; DAS routing reads exclusively DAS-local state.
  • No change to P46 cap values. The cap value DAS uses is the static default P46_DEFAULT_CAPACITY_CAP (= 50 in local), set on row creation at ExposureServiceImpl.java:140. After this fix, enforcement happens at that static cap. Wiring dynamic cap updates is a separate concern, not blocking this bug.

Backfill

Once increment + decrement timing land, the counter tracks future events correctly. Historical drift requires a one-shot reconciliation sourced from CL truth:

UPDATE csp_demand_allocation_service.csp_zone_exposures z
   SET active_connections = (
     SELECT COUNT(*)
       FROM csp_connection_lifecycle_service.connections c
      WHERE c.current_state = 'ACTIVE'
        AND c.csp_id  = z.csp_id
        AND c.zone_id = z.zone_id
   );

Run during a routing-quiet window or with allocation throttled — routing reads the counter in real time, so a mid-flight backfill against a busy zone risks transient incorrect enforcement.
