Wiom · Change Spec · v1.0 · PM deliverable · GAP-07

Anchor DAS acceptance on CSP slot proposal · remove auto-accept · wire P41

DAS today auto-accepts every allocation atomically (BUG-03's markAutoAccepted) — collapsing UNASSIGNED → ASSIGNED → ACCEPTED into a single step. This violates the D&A OS state machine (L170: "ASSIGNED → ACCEPTED is CSP-initiated") and silently disables P41 (the 2h acceptance window timer never has anything to time out because the state is ASSIGNED for ~0 seconds). This spec restores OS-canonical behaviour: DAS persists in ASSIGNED after routing, TAS creates a candidate, the CSP proposes a slot via the existing /proposeSlot endpoint, and that slot proposal triggers the ASSIGNED → ACCEPTED transition. P41 fires if no slot is proposed within 2h, using the GAP-06 one-canonical-flow cascade. CL stays in REQUESTED throughout DAS-`ASSIGNED` and only transitions to PENDING_INSTALL when the (existing) AllocationAccepted event lands — after the slot proposal.

Author: Ashish Raj  ·  Reviewer: Engineering  ·  Tier: Light
Tier: Light — A1, A2, A5, A8, B5 + Workflow + Wired-layers. Five connected changes: (1) remove DAS auto-accept, (2) new AllocationAssigned event from DAS at the ASSIGNED moment, (3) TAS: add ASSIGNED to enum (deprecate ACCEPTED — no migration) + rename onAllocationAccepted → onAllocationAssigned, (4) new DAS inbound handler for the existing EsInstallSlotSelected → triggers AllocationAccepted → CL T1 (REQUESTED → PENDING_INSTALL), (5) wire P41 (acceptance timeout sweep) with the GAP-06 cascade pattern.
Rows: Required — every row filled or marked N/A with a reason.

Quick Check

7-line triage. Filled last, after the body is complete.
What is changing?
Three coordinated changes. (1) Stop auto-accepting — remove AllocationServiceImpl.markAutoAccepted from the routing flow; allocation persists in ASSIGNED after CSP selection. (2) New outbound event AllocationAssigned from DAS at the ASSIGNED moment — payload identical to today's AllocationAccepted; TAS subscribes to this. TAS-side adjustments: add CandidateState.ASSIGNED to enum (keep deprecated ACCEPTED for backward compat of pre-deploy rows — no SQL migration; new candidates use the new value, old rows keep theirs). Rename onAllocationAccepted → onAllocationAssigned. Candidate still auto-advances ASSIGNED → AWAITING_SLOT_PROPOSAL in same transaction. (3) New inbound handler on DAS for EsInstallSlotSelected (existing TAS outbound event from CandidateWorkflowServiceImpl.proposeSlot). On receipt: DAS transitions ASSIGNED → ACCEPTED, cancels P41 schedule, and emits the existing AllocationAccepted event. CL's existing handler then fires T1 (REQUESTED → PENDING_INSTALL) on receipt of AllocationAccepted — so the customer's "Pending install" moment is now triggered by the CSP's slot proposal instead of by silent auto-accept. Plus: wire the P41 acceptance-timeout sweep with a GAP-06-style cascade — per-connection AWS schedule created on ASSIGNED, cancelled on transition out. DAS sweep emits new ClSystemAcceptanceTimeout to TAS, TAS closes candidate, emits existing EsInstallCancelledByUpstream, DAS reverts to UNASSIGNED and re-routes (P51 added, P195 NOT incremented per FM-DAO-02).
What triggered it?
Per D&A OS L170 + L175, ASSIGNED → ACCEPTED is CSP-initiated and P41 governs the wait. BUG-03's atomic write was the workaround that bypassed this. Effect today: P41 is dead code (sweep wired but state is ASSIGNED for ~0 seconds, never times out); the OS-canonical CSP-confirms-via-system-action semantic is replaced by silent auto-accept; INV-DAO-12's distinction between ASSIGNED and ACCEPTED (immediate re-route vs P49 grace period on CSP exit) is unenforceable.
Blast radius
DAS service (state machine, inbound handler, outbound event class, sweep wiring) · TAS service (subscriber switch + new inbound handler) · CL service (zero change — still receives AllocationAccepted, still fires T1). New AWS EventBridge per-connection schedules for P41 (same pattern as P191 from BUG-02). No DB migration. No customer-app change.
Reversible?
Yes — feature-flag the auto-accept removal; rollback = re-enable markAutoAccepted on the routing path. Event-class additions are additive.
Money / PII / migration?
No / No / No. Going-forward only. Existing ACCEPTED/ACTIVE allocations untouched. In-flight ASSIGNED rows at deploy time get either: re-emit AllocationAssigned to TAS, OR skip if TAS candidate already exists.
OS impact / sign-off?
No OS amendments. This is code-OS realignment back to the canonical state machine at D&A OS L149-175. ESR: confirm AllocationAssigned and ClSystemAcceptanceTimeout event classes are registered.

A2. Why This Change WHAT

What is expected: Observable trigger, who is affected, cost of leaving it.
QuestionAnswer
What's wrong with the current behaviour?Three connected problems. (1) State-machine collapse. AllocationServiceImpl.markAutoAccepted sets allocation_state = ACCEPTED in the same transaction as ASSIGNED (BUG-03 / AMENDMENT-02 design). This skips the ASSIGNED state that the OS state machine declares meaningful (L170: ASSIGNED → ACCEPTED is CSP-initiated). (2) P41 is dead code. The sweep at BatchTriggerServiceImpl:31 queries for ASSIGNED rows older than P41 (2h). Because ASSIGNED lasts ~0 seconds today, the sweep always returns an empty set; P41 has effectively never fired in prod. The OS-mandated FM-DAO-02 (acceptance timeout) and FM-DAO-08 (CSP exits between ASSIGNED and ACCEPTED — immediate re-route) cannot trigger. (3) Acceptance is silent. The CSP "accepts" by no signal — they just do it implicitly when routing picks them. CSP App doesn't know to ask "do you want this booking?" because the answer is structurally "yes." This contradicts the OS view at L163: ACCEPTED = "CSP has confirmed acceptance" (an active confirmation), not "CSP was picked by routing."
Who experiences it?CSPs: can't decline an allocation before slot proposal (no ASSIGNED state to decline from — FM-DAO-11 cannot fire). Customers: get a 2h delay buried in CSP indecision instead of the OS-prescribed re-route after P41 (which would save them up to 2h of waiting on a non-responsive CSP). Operations: can't distinguish "CSP was assigned but didn't act" from "CSP accepted but install hasn't started" — both look the same in DAS data. D&A OS / Quality OS: never receive the DECLINE_PATTERN signal for acceptance timeouts (per FM-DAO-02) because there are no acceptance timeouts.
Cost of leaving it as-is?P41 stays inert; the OS-canonical "CSP confirms" semantic stays silent. Every booking gets the auto-accept happy path; bookings with non-responsive CSPs sit in PENDING_INSTALL for up to P74 (72h) instead of being re-routed at P41 (2h) — a 36× delay for the customer.

DAS — new inbound handler for EsInstallSlotSelected → CL cascade to PENDING_INSTALL DAS has no inbound handler for EsInstallSlotSelected. The event fires today (from CandidateWorkflowServiceImpl.proposeSlot at line 270, emitted as part of the slot-proposal flow) but DAS doesn't listen. CL stays in REQUESTED with no signal that the slot was proposed. New endpoint + handler. On receipt: (a) validate connection is in allocation_state = 'ASSIGNED', (b) transition to ACCEPTED, (c) set acceptance_timestamp = now, (d) cancel the P41 schedule for this connection, (e) emit the existing AllocationAccepted event to CL. CL's existing handler then fires T1: connections.current_state: REQUESTED → PENDING_INSTALL, writes connection_event_history row (event_type=ALLOCATION_ACCEPTED, source_os=DEMAND_ALLOCATION_OS, previous_state=REQUESTED, resulting_state=PENDING_INSTALL), and emits ClStateChanged downstream. This is the CL transition that was happening at routing time (~0s) under auto-accept — it now happens at slot-proposal time (~minutes/hours later) instead. Slot proposal is the OS-canonical CSP-acceptance signal. EsInstallSlotSelected already carries the connection_id + csp_id. AllocationAccepted is the existing CL trigger — it just arrives later in the chain. CL's T1 transition is the visible outcome of slot proposal — the customer's "PENDING_INSTALL" moment.
CL — zero code change (T1 trigger relocated in time, not in source) CL receives AllocationAccepted ~0s after routing, fires T1 (REQUESTED → PENDING_INSTALL), records connection_event_history, emits ClStateChanged. Same handler, same trigger event, same state machine, same transition (T1). Only difference: AllocationAccepted now arrives ~minutes/hours after the assignment (when CSP proposes a slot) instead of ~0 seconds. CL state stays REQUESTED during the DAS ASSIGNED window. Once the slot proposal triggers AllocationAccepted emission from DAS, CL fires REQUESTED → PENDING_INSTALL exactly as today. Smallest possible CL footprint. Customer-app shows "Looking for a provider" during DAS ASSIGNED — same UX text as today's UNASSIGNED case (the customer can't tell the difference). Avoids adding a new CL state for this iteration.
DAS — wire the P41 acceptance-timeout sweep on per-connection schedules (BUG-02 pattern) Sweep batch runAllocationTimeoutSweep exists at BatchTriggerServiceImpl.java:31. Endpoint POST /allocation-timeout-sweep exists. No per-connection AWS schedule is created today (because no allocation ever sits in ASSIGNED long enough to matter, and the AWS scheduler wasn't wired pre-BUG-02). When an allocation transitions to ASSIGNED, DAS creates a per-connection one-time delay AWS schedule with delay = P41 (default 2h). Same pattern as the P191 schedules from BUG-02. When the schedule fires, the dispatcher invokes the timeout sweep for that connection. Schedule is cancelled when the allocation transitions out of ASSIGNED (to ACCEPTED, UNASSIGNED, or DECLINED). Per BUG-02's connection-wise scheduling model. Lets each allocation get its own P41 timer without a global cron.
DAS — P41 sweep emits ClSystemAcceptanceTimeout (new event) to TAS Sweep iterates over ASSIGNED rows older than P41 and calls a handler internally. No outbound TAS event. For each timed-out row, DAS emits a new outbound event ClSystemAcceptanceTimeout(connection_id, csp_id, timestamp, failure_reason=TIMEOUT_P41, source_os=SYSTEM). Does NOT mutate DAS state internally — the cascade comes back via TAS (GAP-06 pattern). One canonical failure flow — TAS is the canonical owner of install candidate state, so DAS routes the system-driven timeout through TAS just like the CSP-reported install failure path.
TAS — new inbound handler for ClSystemAcceptanceTimeout TAS has no handler for this event. Receives ClSystemAcceptanceTimeout, finds the active candidate for the connection, transitions it to CANCELLED_BY_UPSTREAM with reason_code = TIMEOUT_P41, failure_subreason_source = SYSTEM. Then emits the existing EsInstallCancelledByUpstream outbound — DAS consumes that next. Closes the candidate cleanly through TAS's existing state machine. Reuses the existing CANCELLED_BY_UPSTREAM terminal and the existing EsInstallCancelledByUpstream outbound — no new TAS surface beyond the handler.
DAS — new inbound handler for EsInstallCancelledByUpstream DAS has no handler for this event. On receipt with reason_code = TIMEOUT_P41: validate allocation in ASSIGNED, transition to UNASSIGNED, set previous_csp_id = the timed-out CSP, add a P51 cooldown entry for that CSP (per FM-DAO-02: "P51 cooldown applies for that connection"), do NOT increment the P195 counter (per FM-DAO-02: "Timed-out CSP is NOT penalized in this OS"), then trigger routing-engine re-attempt. If reroute succeeds → ASSIGNED with new CSP; if fails → stays UNASSIGNED with the audit log row. Restores the OS-canonical re-routing path on P41 timeout. The "not penalized" detail at FM-DAO-02 is important — distinguishes implicit timeout (CSP didn't act) from active decline (CSP refused), even though both apply P51.
CL during DAS ASSIGNED — no change CL never sees the ASSIGNED state because auto-accept skips it. CL is in PENDING_INSTALL by the time the human would notice. CL stays in REQUESTED for the duration of DAS ASSIGNED (up to P41 = 2h). When acceptance lands, CL receives AllocationAccepted and fires T1. No new CL state to introduce. Customer-app surfaces "looking for a provider" for both UNASSIGNED and ASSIGNED — visual parity with today's UNASSIGNED experience.
BUG-03 relationship. BUG-03 (the atomic ASSIGNED → ACCEPTED write) was an OS-misreading patch driven by the D&A OS pseudocode at L440 (emit ALLOCATION_ACCEPTED right after CSP selection). The pseudocode contradicted the state machine rules at L170 (acceptance is CSP-initiated) and the offer-conversion tracking at L474 (offers_claimed = count(ALLOCATION_ACCEPTED events) — counts true acceptances, not selections). This spec aligns the implementation with the state-machine-canonical reading. No D&A OS amendment required — the state machine was always the truth; the pseudocode was loose.
P41 sweep cascade — explicit no-loop principle. Same as GAP-06's P74 fix: DAS does NOT mutate its own state on the system-driven timeout. The cascade goes DAS → TAS → DAS, with TAS owning the candidate closure and DAS resuming routing only when the downstream event echoes back. CL is uninvolved (it stayed in REQUESTED throughout). No double-processing, no echo loop.
Out of scope: Customer-app surface that distinguishes "no provider yet" (UNASSIGNED) from "provider assigned, awaiting slot" (ASSIGNED). Both render the same way today — surfacing this requires a separate Customer-app spec. Renaming AllocationAccepted for semantic clarity (we keep the name; only the moment of emit changes).

  And   EsInstallSlotSelected is published just before the P41 timeout fire

        (transaction-isolation guarantees serializability)
  And   the loser is treated as a late event (LOGIC-5 path)

  When  an allocation enters ASSIGNED and the schedule fires soon after
