Wiom · Change Spec · v1.0 · PM deliverable · GAP-11

WhatsApp fallback for undelivered install-task PNs, via task deeplink

Push-notification delivery for the New Installation task sits at ~88% today — meaning roughly 1 in 8 CSPs never sees the task push and discovers new work only by opening the feed. The fix: the install_task_created CleverTap event (already fired by csp-notification-service on every candidate creation) additionally carries a deeplink URL to the task; a CleverTap journey sends a WhatsApp message carrying that link when the PN is not delivered within a CT-configured window (initial value 10 minutes). The app's deeplink rail — App Links intent-filter, DeepLinkRouter, and the openPage routing path — already exists and needs no structural change; what remains is hosting assetlinks.json plus a browser fallback to the APK download, correct entry_source attribution on install_candidate_opened (today every open is misattributed as home_card), and a toast when the linked task no longer exists.

Author: Ashish Raj  ·  Reviewer: Engineering  ·  Tier: Medium
Tier: Medium — A1, A2, A5, A6, A8, B5 (incl. REGRESSION blocks) + Workflow + Wired-layers. 6 connected changes: (1) deeplink property added to install_task_created, (2) host assetlinks.json on csp.wiom.in, (3) browser fallback on csp.wiom.in redirects to the APK download, (4) entry_source threaded through the app's drilldown-open rail (pn / deeplink / home_card), (5) task-not-found opens land on HOME with a toast, (6) CT journey sends WhatsApp with the deeplink when the PN is undelivered within the CT-configured window.
Rows: Required — every row filled or marked N/A with a reason.

What is changing?
(1) csp-notification-service adds a deeplink property to install_task_created; (2)+(3) a new web endpoint on csp.wiom.in serves /.well-known/assetlinks.json and 302-redirects browser opens to the APK download; (4) the CSP app attributes drilldown opens with entry_source = pn / deeplink / home_card (today everything is home_card); (5) task-not-found opens show a toast instead of failing silently; (6) a CT journey sends a WhatsApp message with the deeplink when the PN is undelivered within the CT-configured window.

Blast radius

No DB migration. No ES / OS state-machine change. No customer-app change. Existing PN payload and campaign untouched.
Reversible?
Yes — the event property is additive; the CT journey can be paused from the dashboard; app changes are attribution + toast only (no flow change).
Money / PII / migration?
Money: No. PII: No — the deeplink carries only execution_candidate_id (opaque ID; consistent with ASM-ES-INSTALL-05, no customer mobile anywhere in the link). Migration: No.
OS impact / sign-off?
None — csp-notification-service is a read-only fan-out consumer; no OS event contract, state, or timer changes. No OS amendments.

A2. Why This Change WHAT

What is expected: Observable trigger, who is affected, cost of leaving it.
QuestionAnswer
What's wrong with the current behaviour?
  1. ~12% of New Installation task PNs are never delivered (delivery ~88%, in line with the 80–90% industry norm — but each miss is a CSP who doesn't know a task exists). There is no fallback channel today.
  2. No clickable link exists outside the app. install_task_created (EventTranslator.java:83–91) carries execution_id and page_name but no https URL, so a WhatsApp/SMS message today could not take the CSP to the task.
  3. Open-source attribution is broken. Every drilldown open — feed tap, PN tap, future deeplink tap — funnels through onCardBodyClick, which hard-codes entry_source="home_card" (HomeViewModel.kt:2501). PN-driven opens are indistinguishable from feed opens, so a fallback channel's contribution would be unmeasurable.
  4. A dead link fails silently. If the routed task is no longer in the feed (cancelled / reassigned / expired), navigateToDrilldown logs and stays on HOME with no user-visible explanation (HomeViewModel.kt:2343).
Who experiences it?CSP — learns about a new installation task late (or only on next feed open), delaying slot proposal. Customer — waits longer for first CSP contact after booking. PM/analytics — cannot separate PN-driven opens from organic feed opens, so PN reach experiments can't be evaluated.
Cost of leaving it as-is?~12% of new install tasks start with a delayed first-touch. Every hour of delay in slot proposal compounds through the booking→install funnel (auto-confirm and expiry timers keep running regardless of whether the CSP knows the task exists).

A5. The Delta WHAT

What is expected: One row per atomic change: what changes → before → after → why.
What changesBeforeAfterWhy
1 · csp-notification-service — add deeplink property to install_task_created translateInstallCandidateCreated (EventTranslator.java:83–91) puts execution_id, zone_id, csp_role, spine (source_event, source_event_id, csp_id, page_name=INSTALL_TASK_DRILLDOWN). No URL of any kind. Same method additionally puts deeplink = "https://csp.wiom.in/task/install/" + e.executionCandidateId(). All existing properties unchanged. The WhatsApp template needs a clickable https URL. The path segment matches the app's DeepLinkRouter registry entry /task/install/<taskId> (DeepLinkRouter.kt:137–140) verbatim — no new route on the app side. The full URL travels as one property (rather than CT assembling it from execution_id) so the path shape has a single source of truth in code, not in N dashboard templates.
2 · Deeplink web service (new) — host assetlinks.json Nothing served at https://csp.wiom.in/.well-known/assetlinks.json. The manifest's autoVerify fails silently and Android shows an app-chooser instead of opening the app directly (documented in AndroidManifest.xml:70–74, note D-02). assetlinks.json served at that path, declaring the CSP app package name + release-signing-key SHA-256 fingerprint. Verified App Links are what make a WhatsApp link open the app in one tap with no chooser. This was already anticipated by the app team (D-02) — the hosting side was never built.
3 · Deeplink web service (new) — browser fallback → APK download No handler exists on csp.wiom.in; if the app is not installed, the link opens in a browser and dead-ends. Any browser GET on /task/install/* (and, as default, any other path) responds 302 Location: https://wiom-partner.s3.ap-south-1.amazonaws.com/Wiom-CSP.apk. PM decision: the no-app case (not installed, or an old app version without the App Links filter) should land the user on the app download. A static host/CDN redirect rule is sufficient; implementation choice is engineering's.
4 · CSP app — thread entry_source through the drilldown-open rail onCardBodyClick fires install_candidate_opened with hard-coded entry_source="home_card" (HomeViewModel.kt:2501). PN-routed opens (via openPage → navigateToDrilldown → onCardBodyClick) are therefore recorded as home_card. The openPage rail carries no source information. entry_source becomes a parameter carried from the entry point: push-payload route (MainActivity.parsePageNameFromIntent) → pn; external App Link route (MainActivity.parseDeepLinkFromIntent → DeepLinkRouter.handleResult) → deeplink; direct feed tap → home_card (default, unchanged); FPN overlay CTA → fpn (already fired separately today — untouched). Applies to all four typed *_candidate_opened events since they share onCardBodyClick, but only install has non-feed entry points in scope here. PM requirement: PN-opened → source pn; deeplink-opened → source deeplink (reserved exclusively for link taps). Without this the WhatsApp fallback's contribution is unmeasurable — which is the point of the experiment. Values follow the existing noun style of home_card/fpn.
5 · CSP app — task-not-found toast navigateToDrilldown silently stays on HOME when execution_id isn't found after a forced feed refresh (HomeViewModel.kt:2343 — log line only). Same fallback (land/stay on HOME feed) plus a user-visible toast: “This task does not exist” (final copy/translation with content team). One toast for all not-found causes — terminal-state task, reassigned task, unknown ID. PM decision: a CSP who taps a WhatsApp link hours later must get an explanation, not a silent landing on HOME. One undifferentiated toast — the app cannot (and should not) distinguish why the task is gone from the feed alone.
6 · CleverTap config — WhatsApp fallback journey (dashboard, not code) A single PN campaign triggers on install_task_created. No fallback branch. Journey: trigger on install_task_created → wait window defined on CT (initial value 10 min) → branch on CT's push-delivery signal → if undelivered, send WhatsApp template to the CSP's profile number with CTA URL = {{deeplink}} event property. Delivered branch: exit, no message. Reaches the ~12% whose PN never lands. The window is a CT-dashboard setting so ops can tune it without a release. WhatsApp channel/BSP integration already exists on CT (PM-confirmed); template authoring and approval is part of this journey setup.
Relationship to existing rails: rows 2–4 complete work the app already shipped — the App Links intent-filter, DeepLinkRouter, and the parseDeepLinkFromIntent hook all exist in the current development branch (see WR). This spec adds no new route, screen, or navigation mechanism; the PN tap path itself (page_name/execution_id push extras) is untouched — PN messages do not need the https deeplink, they already route natively.
