Wiom · Change Spec · v1.0 · PM deliverable · GAP-02

Change technician at any active state (Install only)

The CSP can swap the assigned technician any time after initial assignment, until the install candidate reaches a terminal state. That is the seven in-flight states from TECHNICIAN_ASSIGNED through RATING_PENDING. Today the install state machine wires the self-loop only at TECHNICIAN_ASSIGNED; this spec extends it to all seven, exposes ASSIGN_TECHNICIAN in the allowed-actions API, populates the gateway flag, and surfaces the CTA in the CSP App.

Author: Ashish Raj  ·  Reviewer: Engineering  ·  Tier: Light
Tier: Light — A1, A2, A5, A6, A8, B5. State-machine extension on an existing action, allowed-actions surface, UI exposure.
Rows: Required — every row filled or marked N/A with a reason.

Quick Check

7-line triage. Filled last, after the body is complete.
What is changing?
Allow technician swap (ASSIGN_TECHNICIAN) at all 7 in-flight install states where a technician is already assigned: TECHNICIAN_ASSIGNED, ARRIVED_AT_SITE, INSTALLATION_IN_PROGRESS_PRE_FEE, FEE_COLLECTION_PENDING, INSTALLATION_IN_PROGRESS_POST_FEE, AWAITING_CUSTOMER_OTP, RATING_PENDING.
What triggered it?
Partner feedback — CSPs need to swap technicians not just before arrival but also during on-site work (sick mid-install, swap to a senior tech for a tricky fee collection, etc.). State machine has the self-loop only at TECHNICIAN_ASSIGNED today.
Blast radius
Install state machine (6 new self-loops) · TAS allowed-actions resolver (7 case branches) · Gateway TaskDrilldown.can_reassign (currently null) · CSP App install drilldown.
Reversible?
Yes — the new self-loops + allowed-actions entries can be removed; only the existing TECHNICIAN_ASSIGNED self-loop predates this change.
Money / PII / migration?
No / No / No.
OS impact / sign-off?
None — candidate state machine lives in the install ES, not in a higher-level OS. Adding self-loops on an existing action is a behaviour-change in the ES, documented in ES PRD.

A2. Why This Change WHAT

What is expected: A short problem statement.
All rows required
QuestionAnswer
What's wrong with the current behaviour?The install state machine wires (TECHNICIAN_ASSIGNED, ASSIGN_TECHNICIAN) → TECHNICIAN_ASSIGNED only (line annotated "// reassign"). The CSP can't swap after the tech has arrived at site, during the install steps, during fee collection, during the OTP step, or during rating — even though a technician is assigned and the candidate is still active. Compounding this, even at TECHNICIAN_ASSIGNED the swap is hidden: TasCandidateQueryServiceImpl.resolveAllowedActions(TECHNICIAN_ASSIGNED) returns only [MARK_ARRIVED], so the API doesn't tell the CSP App the action is available. Gateway's TaskDrilldown.can_reassign field is hard-coded null; CSP App's TaskDetail.canReassign defaults false.
Who experiences it?CSPs running multi-technician operations — initial pick falls sick mid-install, senior tech needed for a tricky fee-collection conversation, route shuffle requires moving the booking to a closer tech who's now free.
Cost of leaving it as-is?The CSP has no in-app path to swap mid-flow — either marks the install failed (destructive: customer gets re-allocated to a different CSP entirely) or completes the install with the wrong tech (operational pain, possible quality issue).

Install state machine — ASSIGN_TECHNICIAN self-loops Only one self-loop wired: (TECHNICIAN_ASSIGNED, ASSIGN_TECHNICIAN) → TECHNICIAN_ASSIGNED. Six additional self-loops added — one for each of the other 6 active states in the table above. Each: (state, ASSIGN_TECHNICIAN) → state. Lets the workflow accept the swap action at any active state where a technician is assigned.
TAS allowed-actions resolver — resolveAllowedActions(state) TECHNICIAN_ASSIGNED returns [MARK_ARRIVED]; the six other active states return List.of() (empty). Each of the 7 states returns its existing action list PLUS ASSIGN_TECHNICIAN. For the empty-list states, the result is [ASSIGN_TECHNICIAN]. For TECHNICIAN_ASSIGNED, the result is [MARK_ARRIVED, ASSIGN_TECHNICIAN]. Exposes the swap action on the API surface so the CSP App can render the CTA.
Gateway TaskDrilldown.can_reassign for install Always null (the 6th null in the install-specific block of HomeFacadeService's new TaskDrilldown(...) call). Either populated from the install card's allowed_actions (true iff the list contains ASSIGN_TECHNICIAN) OR the field is dropped entirely and the CSP App reads allowed_actions directly. Engineering's call — latter is cleaner. Either fix the dedicated flag or rely on allowed_actions. Both work; pick one.
CSP App install drilldown UI No "Change technician" CTA at any state. CTA visible at each of the 7 active states when allowed_actions contains ASSIGN_TECHNICIAN. CTA reuses the same technician picker as the initial-assignment flow. Surface the action; reuse the existing picker.
Notification to the newly-assigned technician No swap path exists today. New tech receives whatever standard install-assignment notification path the initial-assignment flow uses. Same path, same payload shape. Re-use existing mechanism; don't invent a new one.
ES PRD allowed-actions table Documents the current per-state allowed-actions (only MARK_ARRIVED at TECHNICIAN_ASSIGNED, empty at the 6 post-arrival states). Documents the expanded allowed-actions: ASSIGN_TECHNICIAN available at all 7 active states from TECHNICIAN_ASSIGNED through RATING_PENDING. PM-side spec matches API behaviour.
Out of scope — explicitly: pre-tech-assignment states (ACCEPTED, AWAITING_SLOT_PROPOSAL, SLOT_SELECTED, AWAITING_CUSTOMER_SLOT_CONFIRMATION, SLOT_CONFIRMED_BY_CUSTOMER, SLOT_AUTO_CONFIRMED, AWAITING_TECHNICIAN_ASSIGNMENT) — no technician is assigned yet, so swap is logically n/a. The existing (AWAITING_TECHNICIAN_ASSIGNMENT, ASSIGN_TECHNICIAN) → TECHNICIAN_ASSIGNED initial-assign transition is unchanged. Also out of scope: Restore + NBREC families, system-initiated reassignment, CSP-to-CSP reassignment, customer notification about the swap, swap-to-self / un-assign (Install has no SELF assignee concept today).

B5. Acceptance Criteria — Verification Layer HOW

What is expected: Given / When / Then blocks covering business logic, use / edge cases, plus a REGRESSION block per A6 guard. Plus a coverage matrix.

Business logic

LOGIC-1: CSP changes the technician at any of the 7 active install states
  Real-world: the original technician is unavailable (rostered off, ill, out of capacity)
  and the CSP needs to assign someone else without restarting the booking.

  Given an install candidate in any of these 7 states:
        TECHNICIAN_ASSIGNED, ARRIVED_AT_SITE, INSTALLATION_IN_PROGRESS_PRE_FEE,
        FEE_COLLECTION_PENDING, INSTALLATION_IN_PROGRESS_POST_FEE,
        AWAITING_CUSTOMER_OTP, RATING_PENDING
  When  the CSP taps "Change technician" and picks technician Y
  Then  the candidate's assigned_technician becomes Y
  And   the candidate state is unchanged (self-loop)
  And   technician Y receives the standard install-assignment notification
        (same path as initial assignment)

  Verify:
    • DB — csp_tas_service.install_execution_candidates
        WHERE execution_candidate_id = <test candidate_id>
        → expect current_state unchanged · assigned_technician_id = <Y>
    • DB — csp_tas_service.install_state_transition_log
        WHERE candidate_id = <test candidate_id> ORDER BY created_at DESC LIMIT 1
        → expect a self-loop row, action = 'ASSIGN_TECHNICIAN'
    • App (Technician Y) — booking now appears in Y's active-assignments list
LOGIC-2: Allowed-actions surface — the swap CTA shows up at all 7 active states
  Real-world: for the "Change technician" button to render in the CSP App, the
  gateway drilldown response must include ASSIGN_TECHNICIAN in allowed_actions for these states.

  Given a candidate in any of the 7 active states
  When  the CSP App fetches the drilldown
  Then  allowed_actions includes ASSIGN_TECHNICIAN
  And   the existing per-state actions are also still present
        (e.g. MARK_ARRIVED at TECHNICIAN_ASSIGNED is unchanged)
  And   can_reassign reflects this (true) — or the dedicated flag has been dropped per A5 row 3

  Verify:
    • API — GET gateway drilldown for each of the 7 active states
        → allowed_actions contains ASSIGN_TECHNICIAN
        → existing per-state actions still present (no replacement)
    • App — "Change technician" CTA visible at each of the 7 states
LOGIC-3 (negative): No swap CTA at pre-technician-assignment states
  Real-world: before a technician is even assigned, there's nothing to swap.
  Initial-assignment is a separate, existing flow.

  Given a candidate in any pre-tech-assignment state
        (ACCEPTED, AWAITING_SLOT_PROPOSAL, SLOT_SELECTED,
         AWAITING_CUSTOMER_SLOT_CONFIRMATION, SLOT_CONFIRMED_BY_CUSTOMER,
         SLOT_AUTO_CONFIRMED, AWAITING_TECHNICIAN_ASSIGNMENT)
  When  the CSP App fetches the drilldown
  Then  allowed_actions does NOT contain a swap-style ASSIGN_TECHNICIAN
        (initial-assign at AWAITING_TECHNICIAN_ASSIGNMENT is the existing assign-flow, not a swap)
  And   the swap CTA is suppressed in the UI

  Verify:
    • API — GET gateway drilldown for each pre-tech state
        → allowed_actions does NOT contain swap-style ASSIGN_TECHNICIAN
        → at AWAITING_TECHNICIAN_ASSIGNMENT the existing initial-assign action remains
    • App — CSP App at pre-tech states shows no "Change technician" CTA
LOGIC-4 (negative): Swap blocked at all 6 terminal states
  Real-world: once the install has reached a terminal outcome (active / cancelled
  / failed / expired), there's no install left to reassign.

  Given a candidate in any terminal state
        (CONNECTION_ACTIVE, INSTALLATION_CANCELLED_ONSITE, INSTALLATION_REPORTED_FAILED,
         CANCELLED_BY_CUSTOMER, CANCELLED_BY_UPSTREAM, INSTALLATION_EXPIRED)
  When  the CSP attempts to swap (via API or UI)
  Then  the state machine rejects the transition
        (no self-loop added at any terminal)
  And   the UI does not show the CTA

  Verify:
    • API — POST swap endpoint for each of 6 terminal states
        → expect 4xx (existing terminal-state guard, same error code as today)
    • DB — install_execution_candidates row unchanged after the attempt
    • App — CTA not shown for terminal candidates

Use & edge cases

EDGE-1: Rapid sequential swaps (X → Y → Z within seconds)
  Real-world: a CSP changes their mind mid-flow and swaps technicians twice quickly.

  Given a candidate at any of the 7 active states
  When  the CSP swaps X→Y then Y→Z within a few seconds
  Then  each swap fires a fresh assignment notification to the new pick
  And   the candidate's assigned_technician tracks the final value (Z)
  And   the state stays at the original active state (self-loop)

  Verify:
    • DB — csp_tas_service.install_state_transition_log
        WHERE candidate_id = <test candidate_id> AND created_at > <test start>
        → expect 2 self-loop rows (X→Y, Y→Z), each with action='ASSIGN_TECHNICIAN'
    • DB — install_execution_candidates → assigned_technician_id = Z (final)
    • App (Z) — booking present in Z's active list
    • App (X, Y) — booking absent from both
EDGE-2: Swap mid-fee-collection
  Real-world: the original technician hits trouble collecting the security fee
  (customer hesitation, pricing question); the CSP swaps to a senior technician.

  Given a candidate in FEE_COLLECTION_PENDING with technician X handling the conversation
  When  the CSP swaps to a senior technician Y
  Then  Y is now the assigned technician
  And   the candidate stays at FEE_COLLECTION_PENDING (self-loop)
  And   X's app removes the candidate from the active list on next refresh
  And   Y's app sees the candidate ready for fee collection
        (any in-progress fee-collection state is reconciled per existing rules — out of scope here)

  Verify:
    • DB — install_execution_candidates → current_state = 'FEE_COLLECTION_PENDING' (unchanged), assigned_technician_id = Y
    • App (X) — booking gone from X's active list
    • App (Y) — booking present, ready to resume fee collection
EDGE-3: Swap during AWAITING_CUSTOMER_OTP
  Real-world: the OTP has been sent to the customer's phone; the CSP needs to
  swap the technician. The pending OTP is tied to the customer, not the technician.

  Given a candidate at AWAITING_CUSTOMER_OTP and the OTP has been sent to the customer
  When  the CSP swaps the technician
  Then  the swap succeeds (state stays at AWAITING_CUSTOMER_OTP)
  And   the pending OTP is unaffected (it's tied to the customer, not the technician)
  And   when the customer enters the OTP, the verification proceeds with the new technician as the actor

  Verify:
    • DB — install_execution_candidates → current_state = 'AWAITING_CUSTOMER_OTP' (unchanged), assigned_technician_id = new
    • Functional — customer enters OTP → verification succeeds; verification audit log records the new technician as actor
EDGE-4: Swap-to-self / un-assign (defensive)
  Real-world: if the picker is submitted without a technician selected, the backend
  must reject — there's no "no-tech-assigned" valid state mid-install.

  Given Install has no SELF assignee concept today
  When  the CSP opens the swap picker and tries to submit without a tech selected
  Then  the picker requires a non-null technician (UI validation)
  And   the backend rejects null/empty technician_id with a 400

  Verify:
    • API — POST swap with technician_id = null → expect 400
    • DB — assigned_technician_id unchanged; no transition row created
    • App — submit button disabled until a tech is picked
EDGE-5: Candidate becomes terminal between opening the picker and submitting
  Real-world: while the CSP has the picker open, the customer cancels (or install
  completes). Race condition — the swap must be rejected gracefully.

  Given the CSP has the swap picker open
  When  the candidate transitions to a terminal state (e.g. customer cancels, or install completes)
  Then  if the swap was already submitted, the backend rejects with the terminal-state guard
  And   the UI shows a clear "candidate is no longer active" message
  And   the picker closes

  Verify:
    • API — submitted swap on a now-terminal candidate → 4xx
    • DB — no state change; assigned_technician_id unchanged
    • App — error toast visible, picker closes
EDGE-6: CSP App offline at submit
  Real-world: CSP picks a tech, taps submit, network drops; retry on reconnect.
  By then the candidate may have moved.

  Given the CSP has picked the new technician but the app is offline
  When  connectivity returns and the request is retried
  Then  the swap fires; if the candidate has moved to terminal in the meantime,
        backend rejects with the terminal-state guard
  And   the UI shows a graceful failure

  Verify:
    • Manual test — disable network on the test device, submit swap, re-enable
    • DB — still active: assigned_technician_id updated; terminal: no change, 4xx returned
    • App — clear result for both branches
