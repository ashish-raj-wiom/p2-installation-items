Wiom · Change Spec · v1.0 · PM deliverable · GAP-02

Change technician at TECHNICIAN_ASSIGNED (Install only)

The install state machine already has a (TECHNICIAN_ASSIGNED, ASSIGN_TECHNICIAN) → TECHNICIAN_ASSIGNED self-loop wired (with the comment "// reassign"). But TasCandidateQueryServiceImpl.resolveAllowedActions(TECHNICIAN_ASSIGNED) only returns [MARK_ARRIVED], hiding the swap action. The CSP App therefore has no "Change technician" CTA. Surface the existing capability — Install only, this state only.

Author: Ashish Raj  ·  Reviewer: Engineering  ·  Tier: Light
Tier: Light — A1, A2, A5, A6, A8, B5. Allowed-actions list extension + UI surfacing.
Rows: Required — every row filled or marked N/A with a reason.

Quick Check

7-line triage. Filled last, after the body is complete.
What is changing?
Expose the existing ASSIGN_TECHNICIAN self-loop at TECHNICIAN_ASSIGNED in the install allowed-actions API, and add a "Change technician" CTA on the CSP App install drilldown.
What triggered it?
Partner feedback — multi-tech CSPs need to swap before the assigned tech arrives at site. State machine supports it; gateway hides it.
Blast radius
TAS install resolveAllowedActions · Gateway TaskDrilldown.can_reassign (currently always null) · CSP App install drilldown.
Reversible?
Yes — the allowed-actions entry can be removed; the state-machine self-loop already existed before this change.
Money / PII / migration?
No / No / No.
OS impact / sign-off?
None — state machine already covers the self-loop; the change is in the allowed-actions surface + UI.

A2. Why This Change WHAT

What is expected: A short problem statement.
All rows required
QuestionAnswer
What's wrong with the current behaviour?The install state machine already wires (TECHNICIAN_ASSIGNED, ASSIGN_TECHNICIAN) → TECHNICIAN_ASSIGNED as a swap self-loop (verified — see the line annotated "// reassign" in InstallationStateMachine.java). But TasCandidateQueryServiceImpl.resolveAllowedActions(TECHNICIAN_ASSIGNED) returns only [MARK_ARRIVED] — so the API never tells the CSP App that ASSIGN_TECHNICIAN is a valid next action. The gateway's TaskDrilldown.can_reassign field exists but is hard-coded to null on every install drilldown (verified at HomeFacadeService — the 6th of 6 INSTALL-specific nulls in the constructor block). The CSP App's TaskDetail.canReassign defaults to false.
Who experiences it?CSPs running multi-technician operations whose initial pick becomes unavailable before the tech arrives at site (sick, route conflict, last-minute reassign to a senior tech).
Cost of leaving it as-is?The CSP has to mark the install failed and let DAS reroute — which is destructive for the customer (install gets reassigned to a different CSP entirely, instead of staying with the original CSP under a different tech).

B5. Acceptance Criteria — Verification Layer HOW

What is expected: Given / When / Then blocks covering business logic, use / edge cases, plus a REGRESSION block per A6 guard. Plus a coverage matrix.

Business logic

LOGIC-1: Swap allowed at TECHNICIAN_ASSIGNED
  Given an install candidate in state TECHNICIAN_ASSIGNED with technician X assigned
  When  the CSP taps "Change technician" and picks technician Y
  Then  the candidate's assigned_technician becomes Y
  And   the candidate state stays at TECHNICIAN_ASSIGNED (self-loop)
  And   technician Y receives the standard install-assignment notification
        (same path as initial assignment)
LOGIC-2: Allowed-actions surface
  Given a candidate in TECHNICIAN_ASSIGNED
  When  the CSP App fetches the drilldown
  Then  allowed_actions contains both MARK_ARRIVED and ASSIGN_TECHNICIAN
  And   can_reassign is true (or the dedicated flag has been dropped per A5 row 2)
LOGIC-3 (negative): Swap blocked at later states
  Given a candidate in ARRIVED_AT_SITE or any later in-flight state
        (INSTALLATION_IN_PROGRESS_PRE_FEE, FEE_COLLECTION_PENDING,
         INSTALLATION_IN_PROGRESS_POST_FEE, AWAITING_CUSTOMER_OTP, RATING_PENDING)
  When  the CSP App fetches the drilldown
  Then  allowed_actions does NOT contain ASSIGN_TECHNICIAN
  And   the swap CTA is suppressed in the UI
  And   if a swap is attempted via direct API call, the state machine rejects it
        (no self-loop wired at these states)
LOGIC-4 (negative): Swap blocked at terminal states
  Given a candidate in any terminal state
        (INSTALLATION_REPORTED_FAILED, CANCELLED_BY_CUSTOMER, CANCELLED_BY_UPSTREAM,
         INSTALLATION_CANCELLED_ONSITE, INSTALLATION_COMPLETED)
  When  the CSP attempts to swap (via API or UI)
  Then  backend rejects with the existing terminal-state guard error
  And   the UI does not show the CTA

Use & edge cases

EDGE-1: Rapid sequential swaps (X → Y → Z in seconds)
  Given a candidate at TECHNICIAN_ASSIGNED
  When  the CSP swaps X→Y then Y→Z within a few seconds
  Then  each swap fires a fresh assignment notification to the new pick
  And   the candidate's assigned_technician tracks the final value (Z)
  And   no rate-limit is enforced (UI may debounce as an implementation choice)
EDGE-2: Swap-to-self
  Given Install has no SELF assignee concept today
  When  the CSP opens the swap picker and tries to submit without a tech selected
  Then  the picker requires a non-null technician (UI validation)
  And   the backend rejects null/empty technician_id with a 400
EDGE-3: Booking cancelled mid-picker
  Given the CSP has the swap picker open
  When  the booking is cancelled upstream (customer or system)
  Then  the picker closes; the candidate disappears from the active list
  And   if the swap was already submitted but not yet processed, the backend rejects with the terminal-state guard
EDGE-4: CSP App offline at submit
  Given the CSP has picked the new technician but the app is offline
  When  connectivity returns and the request is retried
  Then  the swap fires; if the candidate has moved off TECHNICIAN_ASSIGNED in the meantime,
        backend rejects with a graceful failure (state-transition not valid)
  And   the UI shows a clear "could not swap — please retry from the current state" message

Regression

REGRESSION-1 (A6 row 1): Initial-assignment flow unchanged
  Given a candidate at AWAITING_TECHNICIAN_ASSIGNMENT
  When  the CSP assigns the initial technician
  Then  the existing flow works exactly as today
        (state transitions to TECHNICIAN_ASSIGNED via the same ASSIGN_TECHNICIAN action;
         the allowed-actions list at AWAITING_TECHNICIAN_ASSIGNMENT is unchanged)
REGRESSION-2 (A6 row 2): No swap at ARRIVED_AT_SITE and later
  Given a candidate in ARRIVED_AT_SITE, INSTALLATION_IN_PROGRESS_PRE_FEE,
        FEE_COLLECTION_PENDING, INSTALLATION_IN_PROGRESS_POST_FEE, AWAITING_CUSTOMER_OTP, or RATING_PENDING
  When  the drilldown is fetched
  Then  allowed_actions has the same value as today (no ASSIGN_TECHNICIAN added)
  And   the swap CTA is not surfaced
REGRESSION-3 (A6 row 3): Terminal-state guards still reject
  Given a candidate in any terminal state
  When  swap is attempted via API
  Then  backend rejects with the existing terminal-state guard error
REGRESSION-4 (A6 row 4): Restore + NBREC unchanged
  Given a Restore or NBREC candidate at the equivalent assigned state
  When  the drilldown is fetched
  Then  allowed_actions for those families is identical to today
        (this change is in install-only code paths)
REGRESSION-5 (A6 row 5): Other actions at TECHNICIAN_ASSIGNED unchanged
  Given a candidate in TECHNICIAN_ASSIGNED
  When  the CSP fires REPORT_INSTALLATION_FAILED (or any other existing transition from this state)
  Then  the transition fires exactly as today
        (adding ASSIGN_TECHNICIAN to allowed-actions doesn't change MARK_ARRIVED, REPORT_INSTALLATION_FAILED,
         CANCELLED_BY_UPSTREAM, or CANCELLED_BY_CUSTOMER behaviour)
