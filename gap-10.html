P75 Should Trigger the Existing Refund + Workflow Chain

When CLOS deactivates a connection on P75 (REQUESTED → DEACTIVATED, no confirmed CSP acceptance in time), booking-service-java never finds out. The customer isn't refunded and no customer-chat workflow fires until booking-service's own, unrelated 14-day check eventually catches it. The fix requires zero changes to the CSP system. CLOS already returns and later re-emits everything booking-service needs (connection_id) — booking-service just isn't using it. On P75: refund the booking fee and/or security deposit, whichever was paid, and trigger the exact same customer-chat workflows that the 14-day check triggers today. Nothing new, nothing different — just triggered on P75 instead of two weeks later.

Author: Ashish Raj  ·  Reviewer: Customer Backend  ·  Tier: Light
Tier: Light — every change is inside booking-service-java. No CSP-side delta, no wired-layers audit, no workflow cascade section: none of that is needed when the CSP system doesn't change. Sections are numbered sequentially within this document.

Quick Check

What's changing?
Only booking-service-java. Capture the connection_id CLOS already returns when a connection is created (currently silently dropped), subscribe to CLOS's existing CL_CONNECTION_DEACTIVATED event, and on P75 trigger the same refund + workflow chain that the 14-day check triggers today.
What triggered it?
CLOS already ends the connection on P75. Nothing tells booking-service, so the customer waits for an unrelated, later check instead.
CSP-side change?
None. See §B1.
Reversible?
Yes — additive: a new field, a new subscription, a new handler.
Money / PII / migration?
Money: refund timing moves earlier, amount unchanged. PII: none new — connection_id is already returned to booking-service today, just not stored. Migration: one new field on the booking record.
Sign-off?
Customer Backend owner. No CSP OS sign-off needed — nothing changes there.

A2. Why This Change WHAT

QuestionAnswer
What's wrong today?CLOS's P75 and booking-service's own refund check run on two independent clocks. When P75 ends the connection first — the common case, since its window is shorter — CLOS already knows the booking is dead, but never says so. Booking-service only finds out when its own, later check eventually fires.
Who's affected?Any customer whose request is deactivated on P75. Their booking looks active, un-refunded, un-serviceable, for however long it takes booking-service's own check to catch up.
Cost of leaving it?Held booking fee / security deposit and a stuck-looking booking, for longer than necessary, for no operational reason — CLOS already has everything needed to trigger the refund immediately.

A3. The Objective WHAT

When P75 hits:
  1. Refund the booking fee and/or security deposit — whichever was actually paid.
  2. Trigger the same customer-chat workflows that already fire when the 14-day check does this today.
That's the entire scope. Not a new refund path, not a new workflow, not a reduced version of the existing one — the same day-14 outcome, just reached on P75 instead.

Part B

How

B1. CSP System (CLOS) — Changes Required HOW

None. Two things CLOS already does, unmodified, are all this spec needs:
Already existsDetail
Returns connection_id synchronouslyWhen booking-service creates a connection, CLOS's response already includes the connection_id it generated (ConnectionRequestResponse, single field). This has always been returned — booking-service's own DTO just doesn't capture it (see §B2).
Emits CL_CONNECTION_DEACTIVATED on P75The existing event already carries connection_id and deactivation_reason = REQUEST_EXPIRED for a P75-driven deactivation. Unmodified, no new field, no new logic.

The one non-code action still needed is registering booking-service as a recipient of this existing event in the routing registry — an infra/config entry, not a change inside CLOS.

B2. Customer Backend — Changes Required HOW

ChangeDetail
1. Capture and store connection_idBooking-service's response DTO for the connection-creation call doesn't include a connection_id field today, so the value CLOS already sends back is silently dropped. Add the field, and persist it against the booking — no such column exists today.
2. New handler for CL_CONNECTION_DEACTIVATEDOn receipt, act only when deactivation_reason == REQUEST_EXPIRED. Resolve the booking via the stored connection_id. If the booking isn't already cancelled or refunded, trigger the existing refund-and-cancel process — the same one the 14-day check calls today — unmodified: refunds the booking fee and/or security deposit (whichever was paid) and fires every customer-chat workflow that already accompanies that process.
3. Cancel the pending 14-day checkOnce P75 has handled the booking, cancel that booking's own pending 14-day check so it doesn't also fire later.
