Wiom · Change Spec · v1.0 · PM deliverable · GAP-10

Notify customer backend on P75 request-expiry deactivation — close the 7–14 day stuck-refund gap

When CL OS's P75 timer expires a connection (REQUESTED → DEACTIVATED, 7 days, no CSP ever accepted), CL already knows the booking is dead — but it tells no one on the customer side. booking-service-java has its own, independent ~14-day timer (fired externally via an SQS message this repo only consumes, never produces) that eventually refunds the booking amount and security deposit. Between day 7 (CL gives up) and whenever the 14-day mechanism fires, the customer is stuck: booking shows as active, no refund, no CSP will ever be assigned. This spec adds customer_id to the existing CL_CONNECTION_DEACTIVATED event and wires a new booking-service consumer that triggers the existing refund/cancel chain immediately on P75 expiry — collapsing the gap from up to 7 days to effectively zero.

Author: Ashish Raj  ·  Reviewer: Engineering  ·  Tier: Medium
Tier: Medium — A1, A2, A5, A6, A8, B5 + Workflow + Wired-layers. §A6 is included (not omitted per the gap-05 v1.2 convention) because this spec extends a shared event contract (ClConnectionDeactivated) already consumed by 5+ services — the existing consumers' contract must provably not break. Five connected changes: (1) add customer_id to the CL_CONNECTION_DEACTIVATED contract (shared-lib + CL-internal record) and populate it at all 4 emit sites, (2) register booking-service-java as a new HTTP subscriber for this event in the routing registry, (3) new inbound endpoint + handler in booking-service-java filtering on deactivation_reason = REQUEST_EXPIRED, (4) wire the handler to the existing full refund chain (BookingService.cancelBooking, shouldFullRefund=true), (5) cancel any pending 14-day TTL refund event for the same booking so it doesn't double-fire later.
Rows: Required — every row filled or marked N/A with a reason.

Quick Check

7-line triage. Filled last, after the body is complete.
What is changing?
CL side (csp-connection-lifecycle-service): add a customer_id field to the CL_CONNECTION_DEACTIVATED event contract (both the shared-lib record consumed cross-service and CL's internal outbound record) and populate it from ConnectionEntity.customerId at all 4 existing emit sites. Registry side: register booking-service-java as a new HTTP subscriber for CL_CONNECTION_DEACTIVATED (external routing-registry config, not CL code). Customer-backend side (booking-service-java): new inbound REST endpoint (mirrors the existing InboundEventController pattern used by D&A/TAS/Quality/Customer-Access/Support-Resolution) that filters strictly on deactivation_reason = "REQUEST_EXPIRED", resolves the booking via customer_id (== booking.accountId, the same correlation key booking-service already sends to CL today), cancels any pending 14-day TTL refund event for that booking, and calls the existing BookingService.cancelBooking(..., shouldFullRefund=true) chain (refunds booking amount + installation amount + security deposit, exactly as the 14-day path does today).
What triggered it?
CL OS's P75 (T_request_expiry, 7 days — Connection_Lifecycle_OS_v1_7_1_LOCKED.md:457) already declares the connection dead and emits CL_CONNECTION_DEACTIVATED, but no consumer today notifies the customer or triggers a refund. The only refund path is booking-service-java's own independent ~14-day mechanism (external SQS trigger this repo only consumes — see A2), which is unaware CL gave up 7 days earlier. Customer is stuck for up to 7 days with an active-looking, un-refundable, un-serviceable booking.
Blast radius
csp-connection-lifecycle-service (event payload + 4 emit sites) · services/shared-libs/csp-event-contracts (contract addition) · external routing registry (new subscriber registration, out-of-repo) · booking-service-java (new endpoint, new handler, new RefundReasons constant). No DB migration on CL side (additive JSON field only). No CSP-app / customer-app UI change — the customer already sees a cancellation + refund notification via the existing cancelBooking flow, just sooner.
Reversible?
Yes. The new customer_id field is additive (existing consumers ignore unknown fields). The new booking-service endpoint can be disabled by de-registering the subscriber in the routing registry, or feature-flagged around the handler body, with zero effect on CL or any other consumer.
Money / PII / migration?
Money: Yes (refund amount, timing moves earlier — same total, not a new liability). PII: Yes — customer_id now travels on an event already fanned out via HTTP to 5+ internal consumers plus, with this change, an external-org repo; confirm this is within existing data-sharing policy (same value already flows the *other* direction today — booking-service → CL — so no new PII class is introduced, only a new direction). Migration: No.
OS impact / sign-off?
No CL OS document amendment — additive payload field, same category of change as BUG-06 (which added customer_id to CL_CONNECTION_ACTIVATED for the same underlying reason: CAEO needed it and it wasn't there). Existing CL_CONNECTION_DEACTIVATED consumers (D&A, TAS/exit, Quality, Customer-Access, Support-Resolution, Visibility per docstring) need no code change — additive field only. Booking-service-java changes are outside CSP-OS governance (separate repo/org boundary) — subject to that team's own review, noted explicitly in §A8.

A2. Why This Change WHAT

What is expected: Observable trigger, who is affected, cost of leaving it.
QuestionAnswer
What's wrong with the current behaviour?(1) CL declares the booking dead at day 7, silently. P75 fires, CL transitions REQUESTED → DEACTIVATED, and emits CL_CONNECTION_DEACTIVATED — but the payload has no customer_id (ClConnectionDeactivated.java, shared-lib, 15 fields, none of them a customer identifier), so even if a consumer wanted to act on it, it structurally couldn't correlate the event to a booking. (2) booking-service-java has no consumer for any CL signal at all. Its only CL integration (CspConnectionService.java) is outbound — it tells CL about CONNECTION_REQUEST and USER_CANCELLATION, but has no inbound listener, webhook, or queue consumer for anything CL-initiated. (3) The only refund trigger booking-service has is a separate, CL-unaware ~14-day mechanism. Investigation into RefundService.java/QueueConsumerService.java found no internal @Scheduled job computing booking age at all — the "14 days" is only a reason-code label (RefundReasons.AUTO_AFTER_14_DAYS, RefundReasons.java:8) attached to a refund fired by an external SQS message (BOOKING_AUTOMATIC_REFUND) whose producer is outside this repo. That external timer runs on its own clock, with no knowledge that CL already gave up on day 7.
Who experiences it?Customers whose booking never gets a CSP: booking looks alive (no cancellation notice, no refund) for up to 7 days after CL has already internally deactivated it, and typically longer until the independent 14-day mechanism eventually fires — a customer calling support in this window has no clean answer ("your booking is cancelled but not yet refunded" isn't true; CL already deactivated it, booking-service just doesn't know). Support/Ops can't explain the state mismatch between "CL says DEACTIVATED" and "booking-service says still active" without cross-referencing two services manually. Finance holds booking amount + security deposit for longer than necessary with no operational reason.
Cost of leaving it as-is?Every P75-expired connection (zero eligible CSP within 7 days — the exact scenario RoutingEngineServiceImpl.java:121-127's GAP-05 comment calls a "service vacuum") produces a customer stuck for the gap between day 7 (CL gives up) and whenever the independent 14-day-labelled mechanism actually fires — up to 7 additional days of held money and an un-cancellable-looking booking, for no operational reason since CL already has all the information needed to trigger the refund immediately.

Add String customerId field. This is the record actually constructed at the 4 emit sites below — must carry the value before it reaches the shared-lib mapping layer / outbox serialization. Keeps CL's internal record and the cross-service contract in lockstep, as they already are for every other field.
CL — populate customerId at all 4 emit call sites InboundEventProcessingServiceImpl.java constructs new ClConnectionDeactivated(...) at 4 sites: line 857 (handleDeactivationComplete, T—P77), line 904 (handleRequestExpired, T9/P75 — this spec's trigger), line 1045 (handleUserCancellation, T9/customer-initiated), line 1404 (inside the P76 pause-expiry cascade). None pass a customer identifier today, even though ConnectionEntity.customerId (ConnectionEntity.java:26-27) is already loaded on the connection object at every one of these call sites. Add connection.getCustomerId() as the customerId argument at all 4 sites — not just the P75 one. Same event class, same field, every deactivation reason should carry it consistently (a consumer must not have to special-case "only REQUEST_EXPIRED carries customer_id"). The field must be populated at every emit site to be a reliable contract — populating it only for P75 would make the shared event's schema conditional on reason code, an inconsistency the next consumer would trip over.
Routing registry — register booking-service-java as a new subscriber CL's HttpRoutingPublisher (HttpRoutingPublisher.java:34-60) fetches the list of subscriber URLs for CL_CONNECTION_DEACTIVATED from an external routing registry at publish time (RegistryRoutingClient.getRoutes(eventType)) and fans the event out via HTTP POST to each. Today's registered subscribers do not include booking-service-java. Add booking-service-java's new endpoint URL (below) as a registered route for eventType = CL_CONNECTION_DEACTIVATED. This is a registry configuration action, not a CL code change — out of this repo's scope but required for the event to ever reach booking-service. CL's delivery mechanism is registry-driven HTTP fan-out (not a message broker booking-service could independently subscribe to) — the only way to add a consumer is a registry entry.
booking-service-java — new inbound endpoint + handler for CL_CONNECTION_DEACTIVATED No inbound consumer of any kind for CSP-side signals exists in this repo. The only CL integration (CspConnectionService.java) is outbound-only. New POST /internal/events/cl-connection-deactivated endpoint, mirroring the InboundEventController pattern already used by CL's other 5 consumers (@PostMapping, @CheckPermission, headers X-Correlation-Id/X-Causation-Event-Id/X-Source-Service). Handler: (a) no-op unless deactivation_reason == "REQUEST_EXPIRED", (b) resolve the booking by matching customer_id against booking.getAccountId().getLongId() (the existing correlation key — see A1), (c) no-op if the booking is already in a terminal/cancelled/refunded state (idempotency — also covers duplicate delivery), (d) otherwise proceed to the next two rows. Filtering strictly on REQUEST_EXPIRED means this handler only ever reacts to CL's own system-driven P75 timeout — never to USER_CANCELLATION (which originates from a customer-initiated path booking-service may have started itself, so reacting to it here would risk a redundant/looping cancel attempt). The existing correlation key removes the need for a new connection_id column on the booking entity (confirmed: MBooking has none today).
booking-service-java — cancel the pending 14-day TTL event before refunding EventSchedulerService.cancelBookingEvent(mobileNumber, eventName) / cancelAllEvents(mobileNumber, excludedEventList) (IEventSchedulerService.java:63,49; impl EventSchedulerService.java:181-193,132-163) exist and are already used elsewhere to cancel a scheduled refund TTL when a booking state changes out from under it — but nothing calls this on receipt of a CL-side deactivation, because no such receipt path exists today. New handler calls cancelAllEvents(mobile, ...) (or the specific booking-refund event name if this booking has one armed) before invoking the refund chain, so the independent 14-day mechanism cannot also fire later and attempt a second refund on an already-cancelled/refunded booking. Without this, the existing 14-day path could still fire afterward — harmless if the refund idempotency guard in cancelBooking holds, but leaves a dangling scheduled event and a confusing audit trail. Cleaner to cancel it explicitly.
booking-service-java — new RefundReasons constant + call into the existing refund chain RefundReasons.java has AUTO_AFTER_14_DAYS (L8), AUTO_REFUND_ON_INSTALLATION_NOT_COMPLETED (L13), BOOKING_STUCK_STATE (L16) — no reason code exists for a CL-initiated trigger. Add CL_P75_REQUEST_EXPIRED = "CSP connection request expired (P75) — no CSP accepted within 7 days". Handler builds a cancel request (same shape as RefundService.handleBookingRefund, RefundService.java:240-249: unserviceable=true, isCustomer=false) with this reason and calls BookingService.cancelBooking(request, leadStatus, shouldFullRefund=true) directly — not handleConfigurableRefunds, since that path is designed for admin-configured N-days-after-event TTLs, not an immediate external trigger. cancelBooking (BookingService.java:1350-1582) already implements the full chain this spec needs verbatim: status → UNSERVICEABLE_V2, booking-amount refund (L1428-1453), installation-amount refund (L1486-1504), and — critically — security-deposit refund as a separate REFUND_TRANSACTION message when shouldFullRefund && sdTxnId present (L1506-1523). Reusing it means zero new refund-computation logic, only a new trigger path into code that already works.
Why filter on REQUEST_EXPIRED specifically, not "any DEACTIVATED." CL_CONNECTION_DEACTIVATED fires for at least 4 distinct reasons (P75 expiry, customer-initiated cancellation, P77 deactivation-timeout completion, P76 pause-expiry cascade). Only P75/REQUEST_EXPIRED represents "CL decided this on its own, customer-side has no idea" — USER_CANCELLATION in particular is very likely to already originate from a booking-service-initiated cancel (booking-service tells CL via CspConnectionService today), so reacting to it here would either be a harmless no-op (booking already cancelled) or, worse, a redundant refund attempt if the ordering assumption ever breaks. Scoping strictly to REQUEST_EXPIRED keeps this spec's blast radius to exactly the gap described.

B5. Acceptance Criteria — Verification Layer HOW

What is expected: Given / When / Then blocks covering business logic and use / edge cases. Negative checks first-class on every block.

Business logic

LOGIC-1: Happy path — P75 fires, customer refunded same-day instead of up to 7 days later
  Real-world: a booking in a zone with zero eligible CSPs, connection sits REQUESTED for 7 days.

  Given a CL connection in REQUESTED state for <connection_id>, customer_id = <cid>,
        with a matching booking in booking-service in a pre-install, un-refunded state
  When  the P75 AWS schedule fires and CL transitions REQUESTED to DEACTIVATED (REQUEST_EXPIRED)
  Then  CL emits CL_CONNECTION_DEACTIVATED with customer_id = <cid> and deactivation_reason = REQUEST_EXPIRED
  And   the routing registry delivers it to booking-service-java's new endpoint
  And   booking-service resolves the booking via accountId == <cid>
  And   booking-service cancels any pending 14-day TTL event for this booking
  And   booking-service calls cancelBooking(reason=CL_P75_REQUEST_EXPIRED, shouldFullRefund=true)
  And   booking.status transitions to UNSERVICEABLE_V2
  And   a REFUND_TRANSACTION message is sent for the booking amount
  And   a REFUND_TRANSACTION message is sent for the security deposit (if sdTxnId was present)
  And   the customer receives the existing cancellation/refund notification

  Verify:
    • CL outbox — exactly 1 CL_CONNECTION_DEACTIVATED row with customer_id populated
    • booking-service DB — booking.status = UNSERVICEABLE_V2, refund fields populated
    • booking-service outbox/queue — REFUND_TRANSACTION messages for booking amount + SD (if applicable)
    • Negative — no second refund attempt later from the (now-cancelled) 14-day TTL path
LOGIC-2: USER_CANCELLATION must NOT trigger this handler
  Real-world: customer cancels via the app; CL deactivates via a different reason.

  Given CL emits CL_CONNECTION_DEACTIVATED with deactivation_reason = USER_CANCELLATION
  When  booking-service-java's new endpoint receives it
  Then  the handler no-ops immediately on the reason filter
  And   no refund/cancel logic is invoked from this path

  Verify:
    • booking-service logs — explicit "skipped, reason != REQUEST_EXPIRED" log line
    • Negative — zero calls into cancelBooking from this handler for this event
LOGIC-3: Booking already cancelled/refunded by the time the P75 event arrives
  Real-world: customer cancelled directly through the app moments before P75 fired; both paths race.

  Given the booking for customer_id = <cid> is already in a cancelled/refunded terminal state
  When  the P75-triggered CL_CONNECTION_DEACTIVATED event arrives
  Then  the handler's idempotency check finds the booking already terminal
  And   no second cancelBooking call is made, no duplicate refund is sent

  Verify:
    • booking-service DB — exactly one refund transaction total for this booking, not two
    • Negative — no duplicate REFUND_TRANSACTION message
LOGIC-4: customer_id in the event doesn't match any booking (orphan/race/test-data case)
  Real-world: stale connection from test data, or a booking deleted independently of CL.

  Given a CL_CONNECTION_DEACTIVATED event with customer_id = <cid> and reason REQUEST_EXPIRED
  And   no booking in booking-service matches accountId = <cid>
  When  the handler processes the event
  Then  it logs a WARN (not silent) and returns without error
  And   the HTTP response to CL's fan-out is still a success (this is not CL's problem to retry)

  Verify:
    • booking-service logs — WARN entry naming the unmatched customer_id
    • Negative — no exception propagates, no 5xx returned to the registry's HTTP fan-out

Use & edge cases

EDGE-1: Duplicate delivery of the same event (outbox/registry at-least-once retry)
  Real-world: HTTP fan-out retries on transient failure; same event_id delivered twice.
