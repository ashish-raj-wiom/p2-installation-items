P74 install-timeout sweep + TAS cascade + CSP-app communication

CL OS L456 declares P74 = 72h max in PENDING_INSTALL before system-triggered INSTALLATION_FAILED. The sweep batch exists in code (SchedulingServiceImpl.processInstallTimeoutBatch); no scheduler fires it. When it does fire, the TAS-side cascade doesn't close the active install candidate — leaving it orphan in a non-terminal state. And the CSP needs proactive notification (pre-warning + removal) so a missed-install doesn't disappear from their app without warning. Three coordinated changes: wire the CL P74 sweep, close the TAS candidate via Option 1 (CL emits a system-source event → TAS terminates → existing TAS outbound flows back to CL), and add the CSP-app pre-warning + removal notification surface (content TBD by design).

Author: Ashish Raj  ·  Reviewer: Engineering + Design  ·  Tier: Light
Tier: Light — A1, A2, A5, A8, B5. Three changes: (1) wire CL scheduler for P74 sweep, (2) emit system-source install-timeout event from CL → TAS closes candidate → existing flow resumes, (3) CSP-app pre-warning + removal notifications.
Rows: Required — every row filled or marked N/A with a reason.

Quick Check

7-line triage. Filled last, after the body is complete.
What is changing?
Three wirings. (1) CL scheduler fires processInstallTimeoutBatch() on a recurring cadence (15-min default). (2) When the sweep finds a stuck connection, CL emits a new outbound event ClSystemInstallTimeout to TAS; TAS handler closes the active candidate to INSTALLATION_REPORTED_FAILED with failure_reason=TIMEOUT_P74, failure_subreason_code=CSP_NO_SHOW, failure_subreason_source=SYSTEM, failure_subreason_confidence=HIGH; TAS then emits the existing EsInstallReportedFailed downstream, which CL receives and runs the standard T3 transition (PENDING_INSTALL → REQUESTED). (3) CSP-app gets two notifications — a pre-warning at design-decided threshold (likely ~60h post-PENDING_INSTALL entry, content TBD) and a removal notification at 72h fire.
What triggered it?
Live evidence in QA: 1,090 connections currently stuck in PENDING_INSTALL > 72h (1,067 > 7d, 784 > 30d). 373 TAS install candidates stuck active > 72h in non-terminal states like AWAITING_SLOT_PROPOSAL (218), AWAITING_CUSTOMER_OTP (18), FEE_COLLECTION_PENDING (19). OS-prescribed P74 transitions per FM-CLO-02 + GAP-03 EDGE-1 are not firing.
Blast radius
CL service: scheduler config + new outbound event class + sweep refactor to publish-instead-of-direct-call. TAS service: new inbound handler that closes the candidate and emits the existing EsInstallReportedFailed. CSP App: two new notification events to consume (pre-warning + removal). No DB migration. No Customer App change.
Reversible?
Yes — emissions can be feature-flagged. Rollback = stop scheduling the sweep.
Money / PII / migration?
No / No / No. Going-forward only; the 373 stuck candidates can be cleaned up by the sweep on first run after deploy (or by a one-time manual nudge via the existing POST /process-install-timeout endpoint).
OS impact / sign-off?
No OS amendments. CL OS already declares P74 + the canonical failure payload (L456, L633, L919). GAP-03 EDGE-1 (shipped) already specs the OS-aligned subreason payload for system-driven failures. ESR registration check needed for the new ClSystemInstallTimeout event class.

A2. Why This Change WHAT

What is expected: A short problem statement. Observable trigger, who is affected, cost of leaving it.
All rows required
QuestionAnswer
What's wrong with the current behaviour?Three connected gaps. (1) Scheduler unwired. CL OS L456 declares P74's 72h backstop. SchedulingServiceImpl.processInstallTimeoutBatch() exists and correctly constructs the synthetic event with the OS-prescribed metadata. But no scheduler fires it — same root cause as BUG-01 (AWS_SCHEDULER_ENABLED: false, scheduleRecurring(...) never called). (2) TAS cascade missing. If the sweep did fire, CL's current handler runs T3 internally and emits CL_STATE_CHANGED to TAS. TAS's existing handler at InboundEventProcessingServiceImpl.java:241 only acts on T11/T12 transitions (UPSTREAM_RETRY_TRIGGERS = Set.of("T11","T12")) — T3 lands in the "no action required" branch. The active install candidate stays orphan. (3) CSP-app communication absent. When the booking is removed, the CSP currently gets zero signal explaining why. Design WIP for pre-warning + removal notifications.
Who experiences it?Customer: connection sits indefinitely in PENDING_INSTALL with no resolution. CSP: booking either lingers in CSP-app for weeks despite never being completed, OR (post-fix) disappears suddenly with no warning unless the communication piece ships alongside. Quality OS: CSP_NO_SHOW pattern detection signal never fires per CL OS L633 — feeds LOW_CONVERSION_PATTERN_DETECTED per BDN-DA-01 silently broken. Live QA evidence (2026-06-10): 1,090 connections stuck in PENDING_INSTALL > 72h (1,067 > 7d, 784 > 30d). 373 orphan TAS install candidates > 72h in non-terminal states.
Cost of leaving it as-is?OS-prescribed system-source install-failure path silently absent. Customer waits indefinitely; CSP gets no signal; Quality / D&A pattern-detection blind. This is the "no invisible failure" anti-pattern (INV-DAO-13 in spirit; FM-CLO-02 in letter).

Routed to TAS service inbound (TAS owns the install-candidate state machine — that's where the closure must happen). Matches the OS-prescribed payload taxonomy (CL OS L919, L633, GAP-03 EDGE-1). Keeps TAS as the canonical owner of install_execution_candidates state transitions — same as the CSP-reported flow.
TAS inbound handler — close orphan candidate on ClSystemInstallTimeout TAS does nothing on system-driven P74 timeouts. 373 candidates currently orphan in QA > 72h. TAS handler: find the active candidate for the connection. If found, transition to INSTALLATION_REPORTED_FAILED with the same payload metadata. Emit the existing EsInstallReportedFailed outbound (no new outbound class needed — same one CSP-reported failures use). If no active candidate (already terminal, idempotency case), no-op. Reuses 100% of the existing CSP-reported failure cascade end-to-end. The only difference from a CSP-submitted failure is the trigger source — same payload, same downstream consumers, same terminal state.
CL inbound — process the existing EsInstallReportedFailed when source is SYSTEM CL already handles EsInstallReportedFailed. The handler doesn't distinguish CSP-reported vs SYSTEM-source today — fires T3 either way. That's correct. No change required. The standard T3 transition handles both sources identically. (This row exists in the delta to make explicit that the existing path is reused — the sweep refactor in row 2 hands off via the TAS → CL chain rather than going direct.) No double-handling, no race. Single canonical path through the system regardless of failure source.
CSP-app — pre-warning notification at design-determined threshold CSP sees the booking in their app. No signal that it's approaching auto-removal. At a design-determined threshold (likely ~60h post-PENDING_INSTALL entry; exact timing + content owned by design), a notification fires to CSP App: "Booking X is approaching auto-removal — complete the install or report a failure." Channel (in-app banner vs push vs both) owned by design. Avoids the "booking just disappeared" UX. Gives the CSP a window to act before the system declares CSP_NO_SHOW.
CSP-app — removal notification at 72h fire If the booking ever did get removed, CSP gets no notification. When the P74 sweep fires for a connection, in addition to the chain above, a removal notification fires to CSP App: "Booking X has been removed — install was not completed within 72h." Content owned by design. Delivery mechanism is the Updates-section entry + CleverTap push (rows 7 + 8 below). Closes the loop. CSP sees what happened and why.
Backend — write entry to CSP-app Updates section on overdue trigger No backend write to the in-app Updates feed when a booking goes overdue. CSP has no in-app activity record of the removal. When the P74 sweep fires for a connection (the "going overdue" moment), the backend writes a new entry to the CSP's Updates feed for that booking with the system reason (TIMEOUT_P74 / CSP_NO_SHOW). The Updates feed is the in-app activity surface the CSP already reads. The entry includes connection_id, the OS-prescribed reason, and a short description (content owned by design). Same pattern is also used at the pre-warning threshold (~60h, design TBD) so the CSP sees both the warning and the eventual removal in one place. Gives the CSP a durable in-app record of the threshold event. Survives push-notification miss/dismissal. Aligns with the existing CSP-app pattern where state-affecting events land in Updates as the canonical activity log.
Backend — trigger CleverTap push notification when Updates entry is created No push on this event today. CSP only finds out next time they open the app and notice the booking is gone. Backend creation of the Updates entry (row 7) triggers a CleverTap push notification to the assigned CSP's device. PN payload includes deep-link to the Updates entry; content + template owned by design. Same mechanism for the pre-warning push (different copy). Idempotency: each Updates entry produces exactly one PN (one event = one creation = one PN trigger). Out-of-app surface so the CSP gets the signal without having to be in the app at the moment of the threshold crossing.
Implementation choice for tech (Option 1 vs Option 2): the spec describes Option 1 — CL emits ClSystemInstallTimeout; TAS closes the candidate and emits the existing EsInstallReportedFailed; CL processes that via its existing handler. Option 2 would be: TAS reads T3 + payload.source_os=SYSTEM from the existing CL_STATE_CHANGED stream and acts on it without a new event class (saves the new outbound but requires TAS to learn a second protocol vs the CSP-reported path). Both produce the same OS-mandated outcomes. PM preference is Option 1 — preserves "one canonical flow, only the trigger differs." Tech may overrule if Option 2 is materially simpler given existing code.
Pre-warning timing + content (design WIP): The 60h pre-warning threshold is a placeholder. Design owns the final number and notification content. Two natural decisions: (a) One warning or escalating? Single notif at e.g. 60h, OR a series (e.g. 48h + 60h + 70h). (b) Channel: in-app banner only, push notification only, or both. PM expects design to land these before B5 sign-off.
Out of scope: Wiring the AWS EventBridge / IaC for the scheduler (cross-service infra gap shared with BUG-01 and BUG-02 — tech's responsibility, not scoped per-spec). Customer App notification on the same event (this gap is CSP-app-only; if the customer needs notification too, that's a separate Customer App spec). One-time backfill / cleanup of the 373 orphan candidates currently in QA (running the sweep after deploy resolves them naturally; explicit backfill not required).

State flow — where P74 sits in the CL state machine

The diagram below is the CL state machine, with the P74-driven transition highlighted alongside its sibling transitions. P74 acts as a self-correcting backstop on PENDING_INSTALL — it pushes the connection back to REQUESTED via T3 (the standard install-failure retry path), then D&A retries. If retries exhaust (per P78), T12 escalates to PENDING_DEACTIVATION.

The order of operations matters. The cascade reuses the existing CSP-reported failure flow end-to-end — the only difference is the trigger source (system sweep vs CSP app submission).

        → the removed connection_id is NOT in the response
    • Negative — no removal notification fires for connections that
        have not actually been removed (e.g. those still in the warning window

Use & edge cases

EDGE-1: Sweep cadence boundary — connection ages just past 72h
  Real-world: with a 15-min sweep cadence, a connection that crosses 72h
  precisely between sweeps fires on the next run. Up to 15-min lag is acceptable.

  Given a connection whose state_timestamp puts it at exactly 72h:00m:00s
        (it just crossed the threshold)
  When  the next sweep run executes
  Then  the sweep finds and processes this connection
  And   the total lag (state_timestamp + 72h) → (sweep fire time) is < 15 min

  Verify:
    • Lag metric — for the first sweep firing per deploy, measure
        the median lag from "72h after state_timestamp" to "ClSystemInstallTimeout
        outbox row created_at" → expect < 15 min on a 15-min cadence
EDGE-2: Candidate already terminal when sweep fires (race / idempotency)
  Real-world: the CSP submits an install-complete or install-failure event right
  as the sweep is processing. TAS already closed the candidate. ClSystemInstallTimeout
  arrives late — must be a no-op, not a spurious transition.

  Given ClSystemInstallTimeout arrives at TAS for <test connection_id>
  And   the install candidate is already in a terminal state
        (INSTALLATION_REPORTED_FAILED, INSTALLATION_COMPLETED, CANCELLED_BY_*)
  When  TAS handler processes the event
  Then  the handler is a no-op
  And   no spurious state transition is written
  And   no second EsInstallReportedFailed is emitted

  Verify:
    • TAS candidate (negative) — public.install_execution_candidates
        WHERE connection_id = <test connection_id>
        → expect current_state unchanged from pre-event value
        → expect updated_at unchanged (no spurious write)
    • TAS transition log (negative) — public.install_state_transition_log
        WHERE execution_candidate_id = <candidate id>
          AND occurred_at > <event arrival timestamp>
        → expect 0 new rows
    • TAS outbox (negative) — no new EsInstallReportedFailed row
        emitted for this connection in the relevant window
EDGE-3: Duplicate ClSystemInstallTimeout delivery (broker retry)
  Real-world: message broker delivers the same event twice. TAS handler must
  process exactly once.

  Given the same ClSystemInstallTimeout event (same event_id) is delivered twice
        to TAS for <test connection_id>
  When  TAS processes both deliveries
  Then  exactly one transition occurs
  And   exactly one EsInstallReportedFailed is emitted

  Verify:
    • TAS transition log — expect exactly 1 transition row
        for the candidate in the relevant window
    • TAS outbox — exactly 1 EsInstallReportedFailed row,
        not 2 — relies on TAS's existing idempotency guard
    • CSP-app notification — exactly 1 removal notification
        fires, not 2 (idempotency on the CSP-app receiver side)
EDGE-4: CSP completes install just before P74 cutoff
  Real-world: CSP submits CUSTOMER_INSTALLATION_CONFIRMED right at 71h:50m.
  The connection transitions to ACTIVE before the next sweep run. Sweep must not
  touch already-active connections.

  Given a connection that transitions out of PENDING_INSTALL
        (e.g. to ACTIVE on customer confirmation, or back to REQUESTED on CSP failure)
        before the next sweep run
  When  the sweep runs
  Then  this connection is NOT found by the sweep's query
        (the query filters on current_state = 'PENDING_INSTALL')
  And   no ClSystemInstallTimeout fires for this connection

  Verify:
    • CL outbox (negative) — no ClSystemInstallTimeout for <test connection_id>
        after the connection moved out of PENDING_INSTALL
    • Connection state — public.connections
        → confirm current_state moved out of PENDING_INSTALL before the sweep run
