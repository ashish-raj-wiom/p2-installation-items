§0.1 How to read

Bug format

A bug is a behaviour that the spec already prescribes but the code either never implemented or has broken. Each bug item carries:

  • Original spec citation — file path + section / line reference where the prescribed behaviour lives.
  • Test-case table — one row per Given/When/Then. Three columns: Acceptance criterion · Expected outcome per spec · Observed outcome in prod.
  • Expected-behaviour flow (Mermaid) — included where the flow is non-obvious from the table.
  • Code evidence (collapsed) — pointers to the deviating site for tech to ground the fix.

Gap format

A gap is a behaviour the spec does not cover; PM needs to spec the behaviour change before tech can build. Each gap item uses the Wiom Change Spec template at Light tier (per the Authoring Guide §1.2):

  • Quick Check — 7-line triage header.
  • A1 Metadata · A2 Why This Change · A5 The Delta · A6 Must-Not-Change · A8 OS Impact & Sign-off · B5 Acceptance Criteria + coverage matrix.

Per the Authoring Guide, sections A3 (Current) and A4 (Desired) are skipped at Light tier — A5 then stands alone with self-contained rows.

BUG-01

CLOS timeout scheduler unwired (P75 / P76 / P77 / P78 inert)

BUG

CL OS defines four system-driven timeouts that must fire on background sweeps. The batch methods, endpoints, and scheduler hooks all exist in code — but the AWS EventBridge scheduler is disabled in prod (AWS_SCHEDULER_ENABLED: false) and nothing calls scheduleRecurring(...). Zero system-driven CL transitions in 90 days. P74 is out of scope for this item — its start-time anchor is a separate PM decision.

Original spec: os/Connection_Lifecycle_OS_v1_7_1_LOCKED.md · §5 State Machine (transitions T9, T12 + timeout edges) · SPR params: P75 (7d REQUESTED expiry), P76 (90d PAUSE limit), P77 (45d PENDING_DEACTIVATION), P78 (3 retry cap).
PRD: yaml-prd/connection-lifecycle-prd-v1.6.yaml — state machine + system-source transitions all defined.

BUG-03

DAS allocation state never reaches ACCEPTED (DAS-internal atomic write required)

BUG

AMENDMENT-02 (Apr 2026) deleted the explicit CSP-accept call and declared acceptance "automatic on assignment". DAS has the receiver fully wired (POST /api/demand-allocation/csps/{cspId}/accept + AllocationServiceImpl.acceptAllocation(...)); no service calls it. Result in prod: 0 rows ever in ACCEPTED; 504 / 504 stuck at ASSIGNED / UNASSIGNED; acceptance_timestamp NULL on every row.

Direction (per PM): the fix is a DAS-internal atomic write. When DAS routes an allocation to ASSIGNED, it transitions to ACCEPTED in the same database transaction — no cross-service call, no auto-accept sender to define. AMENDMENT-02's "automatic on assignment" phrasing matches this when read as same-service atomic rather than cross-service deferred. Removes the "who calls who" question entirely.
Original spec: os/Demand_Allocation_OS_v1_9_1_LOCKED.md · §4.1, §4.3 (allocation state machine — ASSIGNED → ACCEPTED transition) · INV-DAO-03 (stickiness post-ACCEPTED).
AMENDMENT-02 (Installation Flow, Apr 2026) — declares acceptance "automatic on assignment" but does not name the sender; this item is the disambiguation.
PRD: yaml-prd/demand-allocation-prd-v1.2.yaml — state + field + transition validation all present.

Test cases — expected vs observed

Acceptance criterionExpected per specObserved in prod
TC-1. When DAS routes an allocation to a CSP, then the allocation row transitions to ACCEPTED with acceptance_timestamp = now(). Allocation row: state = ACCEPTED, acceptance_timestamp set. INV-DAO-03 stickiness now applies — subsequent re-routes blocked. Allocation row: state = ASSIGNED, acceptance_timestamp = NULL. 504 / 504 rows in this state across prod history.
TC-2. When TAS reads the allocation to drive install candidate creation, then it observes ACCEPTED state. TAS reads state = ACCEPTED; install candidate created with confirmed allocation. TAS still creates the install candidate (via the parallel ALLOCATION_ACCEPTED event path), but reads state = ASSIGNED on the allocation row. State and event are out of sync.
TC-3. When the same connection is reallocated after CSP install-failure, then INV-DAO-03 stickiness has already terminated for the prior allocation. Prior allocation row stays in ACCEPTED until install completes or fails. After failure, INV-DAO-03 releases stickiness and the new allocation enters the pipeline. INV-DAO-03 stickiness is inert because nothing reaches ACCEPTED. Re-allocation works by accident, but the guard isn't actually guarding anything.
TC-4. When the routing happy-path completes (DAS picks CSP-A successfully), then the database state-transition ASSIGNED → ACCEPTED happens in a single atomic write. DAS routing engine writes state = ACCEPTED in the same SQL transaction as the initial allocation write. No cross-service call, no auto-accept event. Atomic. Routing engine writes state = ASSIGNED and stops. AMENDMENT-02 deleted the prior cross-service call; the replacement atomic-write was never added.
TC-5. When the integration-spec mentions InstallDasClient.notifyAccepted(), then that class either exists in code OR the integration spec is updated to reflect the atomic-write approach. Integration spec is internally consistent — either the named sender exists, or the spec describes the atomic-write fix. Integration spec at app-specs/das-install-integration-flow.md names InstallDasClient.notifyAccepted() — a class that does not exist in any service. Spec is stale.

BUG-04

Capacity OS skips connection-count increment after installation

BUG

The OS prescribes "Capacity OS counts +1 on T2" in four explicit places. The code guards the increment with if ("RESUME".equals(activationSource)) — so the normal happy-path INITIAL installs silently fall into an empty else branch and the counter doesn't move. Not CSP-app-visible — partner app reads CL directly. Affects internal routing decisions (load-ratio + zone-retire guard) only.

Original spec: os/Connection_Lifecycle_OS_v1_7_1_LOCKED.md · §4.3 T2 (L250): "Consumers: Capacity OS (active count +1), Quality OS (measurement begins), D&A OS (allocation confirmed)…" §4.1 (L202) · §6.3 (L508): identical wording.
os/Capacity_Coverage_OS_LOCKED.md · §2.5: "Counter reflects all ACTIVE connections in the zone, regardless of how they entered ACTIVE state."

Test cases — expected vs observed

Acceptance criterionExpected per specObserved in prod
TC-1. When a connection completes T2 (PENDING_INSTALL → ACTIVE, activation_source = INITIAL), then Capacity OS increments zones.active_connection_count for the zone by 1. Counter advances by 1 per INITIAL T2 event. Code at InboundEventProcessingServiceImpl.java:446-461 gates increment to if ("RESUME".equals(activationSource)). INITIAL hits the else branch with debug log LOG_CONNECTION_ACTIVATION_SKIP. Counter unchanged.
TC-2. When a connection transitions PAUSED → ACTIVE (activation_source = RESUME), then Capacity OS increments the counter. Counter advances by 1. This path works — RESUME hits the if branch correctly.
TC-3. When the load-ratio is computed in the batch-evaluation cycle, then it reads accurate active_connection_count. Load ratio at BatchEvaluationServiceImpl:105 = real ACTIVE / cap. Cap-calibration cycles compute correctly. Load ratio reads stale counter (under-counted for zones with high INITIAL throughput). Cap-calibration cycles miscalibrate.
TC-4. When a zone's last ACTIVE connection deactivates, then guardActiveConnectionCountZeroForRetire allows the zone to retire. Counter reaches 0; retire-guard at ZoneServiceImpl:136 allows zone retirement. If the zone had INITIAL activations that never incremented, the counter may report 0 prematurely (when ACTIVE connections still exist) — or remain stuck at 0 if it was never advanced. Direction of drift depends on RESUME / INITIAL mix.
TC-5. When the CSP partner views their active-connection count on the partner app, then the number matches CL truth. Partner app count = CL connections table count for (csp_id, state=ACTIVE). Already correct — partner app reads CL directly via gateway → CspConnectionQueryController.countByCspIdAndCurrentState. Bypasses Capacity OS entirely. Capacity OS bug doesn't affect this surface.

Backfill

Once the guard is removed, future T2 events increment correctly. Historical drift requires a one-shot reconciliation: UPDATE zones SET active_connection_count = (SELECT count(*) FROM csp_connection_lifecycle_service.connections WHERE current_state='ACTIVE' AND zone_id = zones.zone_id). Run during a window with cap-calibration paused.

A2. Why This Change WHAT

  • What is wrong today: A booking that gets cancelled looks the same in prod whether the customer hit "cancel" in the app or the system auto-cancelled (timeout, supply-vacuum, P78 retry-exhaustion, etc.). Funnel metrics can't separate "customer wanted out" from "we couldn't deliver".

  • Existing exit event for continuity mode. If an exit event is already wired, the new entry emission must not interfere; entries and exits stay symmetric.

B5. Acceptance Criteria — Verification Layer HOW

Business logic

LOGIC-1: Continuity-mode entry detection
  Given a zone with exactly 1 eligible CSP
  When that CSP's cap-ratio reaches >= P_DA_CONTINUITY_CAP_RATIO
  Then DAS transitions the zone to continuity mode
  And  emits SINGLE_PROVIDER_CONTINUITY_ACTIVE with (zone_id, csp_id, cap_ratio, reason, started_at)
  And  emits ZONE_SUPPLY_DEFICIT_SIGNAL with (zone_id, csp_id, severity)

LOGIC-2: Continuity-mode exit detection
  Given a zone in continuity mode
  When the zone gains a second eligible CSP OR cap-ratio drops below threshold
  Then DAS transitions out of continuity mode
  And  emits the existing exit event (symmetric to entry)

LOGIC-3: P46 breach during continuity
  Given a zone in continuity mode where the lone CSP is at P46 cap
  When an allocation would push them over P46
  Then DAS Gate 3e' allows the over-cap allocation (per INV-DAO-17)
  And  emits P46_BREACH_BY_CONTINUITY with (csp_id, zone_id, breach_amount, breach_reason=ENFORCEMENT_REALLOCATION, source_csp_id)

LOGIC-4 (negative): No emission for multi-CSP zones
  Given a zone with > 1 eligible CSP
  When any CSP in the zone hits P46
  Then continuity-mode is NOT entered
  And  no SINGLE_PROVIDER_CONTINUITY_ACTIVE / ZONE_SUPPLY_DEFICIT_SIGNAL is emitted
  And  the over-cap allocation is REJECTED (no P46_BREACH_BY_CONTINUITY signal)

LOGIC-5 (negative): Idempotency on Capacity OS receivers
  Given Capacity OS receives a SINGLE_PROVIDER_CONTINUITY_ACTIVE
  When the same event is delivered twice (e.g. retry)
  Then Capacity OS processes it once (existing idempotency)
       (No PM-side change; verifying receiver behaviour is unchanged.)

Use & edge cases

EDGE-1: Zone enters continuity, exits, re-enters within minutes
  Given a single-CSP zone where the CSP repeatedly hits and drops below the cap
  When continuity-mode toggles on/off rapidly
  Then each entry emits the pair; each exit emits the exit event
  And  no debouncing applied (tech may add debouncing as an implementation choice)

EDGE-2: CSP becomes ineligible while in continuity mode
  Given a zone in continuity mode where the lone CSP gets suspended (e.g. FPV)
  When DAS routing evaluates
  Then the zone moves to "no eligible CSPs" (zero allocation, service-vacuum per OS L540)
  And  the prior continuity-mode signal is NOT re-emitted (already signalled)
  And  ZONE_SUPPLY_DEFICIT_SIGNAL remains the canonical signal for Capacity OS

EDGE-3: P46 breach when continuity-mode entry happens in the same allocation
  Given a single-CSP zone where the first allocation in continuity mode is over cap
  When DAS routes
  Then continuity-mode entry signals fire first
  And  P46_BREACH_BY_CONTINUITY fires as part of the same allocation
       (ordering: entry first, breach second — Capacity OS receives both)

Regression

REGRESSION-1 (A6 row 1): Multi-CSP zones unchanged
  Given a multi-CSP zone
  When routing executes (allocations, retries, sweeps)
  Then no continuity-mode signals fire
  And  routing behaviour is identical to today

REGRESSION-2 (A6 row 2): P46 rejection for non-continuity over-cap allocations
  Given a non-continuity zone with a CSP at or above P46
  When an allocation would push them over P46
  Then DAS rejects the allocation (existing behaviour)
  And  no P46_BREACH_BY_CONTINUITY is emitted

REGRESSION-3 (A6 row 3): Capacity OS receivers idempotent on duplicate events
  Given any of the 3 new events
  When delivered twice (replay or retry)
  Then Capacity OS processes once (existing receiver behaviour)

REGRESSION-4 (A6 row 4): Exit signal symmetric
  Given a continuity-mode entry emission
  When the zone exits continuity (more CSPs / cap drops)
  Then the existing exit event fires with the matching zone_id
