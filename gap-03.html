Wiom · Change Spec · v1.0 · PM deliverable · GAP-03

OS-aligned 6-option failure sub-reason picker + 4-field auto-populate

The Partner App's failure picker exposes 4 reasons today that don't match the OS's failure_subreason_code enum. The picker code reaches the TAS install handler, gets buried in extra_data JSON, then dropped twice more on the way to CL — first because EsInstallReportedFailed doesn't carry the OS sub-reason fields, then because CL's translation handler hard-codes all 4 OS fields to null. Result: every CSP-reported install failure in prod lands at CL with failure_reason = "CSP_REPORTED_FAILURE" and the 4 OS sub-reason fields blank. Replace the picker with the OS-aligned 6 options and propagate the mapping end-to-end.

Author: Ashish Raj  ·  Reviewer: Engineering  ·  Tier: Light
Tier: Light — A1, A2, A5, A6, A8, B5. Enum + handler + event-record + handler-translation change; no state-machine change.
Rows: Required — every row filled or marked N/A with a reason.

What is changing?
Replace the 4-option failure picker with the OS-aligned 6-option enum; populate the 4 OS sub-reason fields (failure_subreason_code, failure_subreason_source, failure_subreason_confidence, failure_detail) end-to-end via a deterministic mapping.
What triggered it?
Verified prod payload: every install-failure event at CL has failure_reason = "CSP_REPORTED_FAILURE" and all 4 sub-reason fields null. Quality OS / Enforcement OS can't do per-CSP pattern detection (BDN-CL-02) when the diagnostic data is blank.

Reversible?
Yes — additive event-record fields; rollback = ignore them.

No / No / No (no retroactive enrichment of historical install-failure rows).
OS impact / sign-off?
No CL OS amendment needed — implementing what CL OS §7.2 / S-02 (v1.2 amendment) already prescribes for the failure_subreason_* fields. ESR doc update for the new EsInstallReportedFailed fields.

A2. Why This Change WHAT

What is expected: A short problem statement.
All rows required
QuestionAnswer
What's wrong with the current behaviour?The TAS picker enum (CancellationReason.java) has 4 options that don't match the OS sub-reason enum: LOCATION_UNREACHABLE, CAPACITY_FULL, CUSTOMER_CANCELLED, TECHNICIAN_UNAVAILABLE. The TAS handler (CandidateWorkflowServiceImpl.reportInstallationFailed) saves the English text in failure_reason and buries the picker code as "report_installation_failed_reason_code" in the candidate's extra_data JSON — it doesn't populate any of the 4 OS-mandated fields. The picker code is then dropped twice more downstream: EsInstallReportedFailed (the event TAS emits to CL) doesn't carry the 4 OS fields; CL's handleEsInstallReportedFailed translation step hard-codes them to null when constructing the internal InstallationFailed event (the field is there in the inbound record, just zero-filled).
Who experiences it?Quality OS pattern detection per BDN-CL-02 collapses (can't differentiate CSP_NO_SHOW from COVERAGE_NOT_FEASIBLE from CUSTOMER_CANCELLED). Enforcement OS per-CSP attribution is similarly blind. Ops doing RCA on install-failure spikes can't filter by cause.
Cost of leaving it as-is?Every CSP-reported install failure in prod lands at CL with the same generic failure_reason = "CSP_REPORTED_FAILURE" and 4 sub-reason fields blank. Per-CSP install-quality attribution is silently corrupted; bonus / penalty signals based on these fields are dark.

The 4-field auto-populate (deterministic mapping)

The CSP's picker selection deterministically drives the 4 OS-mandated fields on every emitted event. Per OS §7.2: failure_subreason_source ∈ {CUSTOMER, CSP, SYSTEM}; failure_subreason_confidence ∈ {HIGH, MEDIUM, LOW}. Picker-driven submissions always carry HIGH confidence (CSP is making a direct, deliberate selection from a finite menu; no inference / no NLP).

Picker = failure_subreason_code→ failure_reason→ failure_subreason_source→ failure_subreason_confidence→ failure_detail

B5. Acceptance Criteria — Verification Layer HOW

What is expected: Given / When / Then per mapping row, plus edges and a REGRESSION block per A6 guard.

Business logic (one per mapping row)

LOGIC-1: COVERAGE_NOT_FEASIBLE mapping
  Given a CSP picks "Location can't be served" (picker code COVERAGE_NOT_FEASIBLE)
  When  the candidate transitions to INSTALLATION_REPORTED_FAILED
        and the chain TAS → CL completes
  Then  the persisted CL event payload has:
        failure_reason             = CSP_REPORTED_FAILURE
        failure_subreason_code     = COVERAGE_NOT_FEASIBLE
        failure_subreason_source   = CSP
        failure_subreason_confidence = HIGH
LOGIC-2: CUSTOMER_CANCELLED maps to CUSTOMER_REFUSED primary
  Given a CSP picks "Customer cancelled" (picker code CUSTOMER_CANCELLED)
  When  the chain TAS → CL completes
  Then  failure_reason             = CUSTOMER_REFUSED   (note: NOT CSP_REPORTED_FAILURE)
        failure_subreason_code     = CUSTOMER_CANCELLED
        failure_subreason_source   = CUSTOMER
        failure_subreason_confidence = HIGH
LOGIC-3: PRICE_CONFUSION maps to CUSTOMER_REFUSED primary
  Given a CSP picks "Customer didn't agree on price"
  When  the chain TAS → CL completes
  Then  failure_reason             = CUSTOMER_REFUSED
        failure_subreason_code     = PRICE_CONFUSION
        failure_subreason_source   = CUSTOMER
        failure_subreason_confidence = HIGH
LOGIC-4: CSP-attributable codes (SCHEDULE_CONFLICT, DEVICE_UNAVAILABLE, BACKHAUL_ISSUE)
  Given a CSP picks any of these three
  When  the chain TAS → CL completes
  Then  failure_reason             = CSP_REPORTED_FAILURE
        failure_subreason_code     = the picker value
        failure_subreason_source   = CSP
        failure_subreason_confidence = HIGH
LOGIC-5 (negative): No null sub-reason on picker-driven submissions
  Given the CSP submits the failure picker with one of the 6 options
  When  the event reaches CL connection_event_history
  Then  failure_subreason_code is NEVER null
  And   failure_subreason_source is NEVER null
  And   failure_subreason_confidence is NEVER null
LOGIC-6: Picker code reaches the persisted CL payload
  Given the Partner App fires POST /install/.../actions/report-installation-failed
        with {reason: "Customer cancelled", reason_code: "CUSTOMER_CANCELLED"}
  When  TAS handler runs → emits EsInstallReportedFailed → CL translates and persists
  Then  connection_event_history.payload for the INSTALLATION_FAILED row
        carries the 4 OS fields populated per the mapping

Use & edge cases

EDGE-1: System-driven failure (P74 timeout) — different code path
  Given a connection times out on P74 (no picker involved)
  When  the CLOS scheduler sweep fires (BUG-01 in the bugs handover; not this item)
  Then  the system path sets:
        failure_subreason_code     = CSP_NO_SHOW
        failure_subreason_source   = SYSTEM
        failure_reason             = TIMEOUT_P74
  And   no picker is shown to anyone (system origin, not CSP-initiated)
EDGE-2: Picker code arrives at TAS as null (defensive)
  Given the Partner App for some reason sends reason_code = null
  When  TAS handler runs
  Then  the handler rejects with HTTP 400 + a clear validation error
        (the picker is REQUIRED; null is not a valid submission)
  And   no candidate transition fires
  And   no downstream event is emitted
EDGE-3: Old app version (pre-rollout)
  Given a CSP runs an app version that fetched the old 4-option picker list
  When  they open the failure picker
  Then  the next GET /install/cancellation-reasons returns the new 6 options
        (server-side change, no client release)
  And   the CSP sees the new list
EDGE-4: EsInstallReportedFailed received from a source that doesn't set the 4 fields
  Given some upstream service emits EsInstallReportedFailed without the new fields
        (e.g. a legacy bridge during rollout)
  When  CL's handleEsInstallReportedFailed runs
  Then  the 4 fields pass through as null (backward-compatible)
  And   the existing T3/T12 flow continues unchanged
        (matches today's behaviour — no regression for legacy senders)

Regression

REGRESSION-1 (A6 row 1): INSTALLATION_REPORTED_FAILED state transition unchanged
  Given any path that fires INSTALLATION_FAILED today (CSP-reported via TAS, or
        system-driven via CLOS scheduler)
  When  the candidate transitions
  Then  the install candidate moves to INSTALLATION_REPORTED_FAILED
        and the downstream T3/T12 logic fires identically to today
REGRESSION-2 (A6 row 2): CL T3 retry + P78 cap unchanged
  Given a translated INSTALLATION_FAILED reaching CL
  When  CL processes
  Then  T3 retry-counter increments per existing rules
  And   P78 retry-cap (3 attempts) enforced per existing rules
  And   the new sub-reason fields don't affect the retry-counter logic
REGRESSION-3 (A6 row 3): System-driven failures unchanged
  Given a system path (P74 timeout etc.)
  When  INSTALLATION_FAILED fires from the system code path
  Then  failure_reason behaves exactly as today (TIMEOUT_P74 etc.)
  And   no picker is involved at any point
REGRESSION-4 (A6 row 4): Old app versions still function
  Given a stale app cache (4-option picker list still locally cached)
  When  the CSP submits via the stale picker
  Then  the picker codes sent are the OLD 4 names
  And   TAS handler maps them to the closest new code (transitional fallback)
        OR rejects with a clear error pointing the CSP at app refresh
        — (engineering picks one; both are acceptable during rollout)
REGRESSION-5 (A6 row 5): Aggregate counts preserved
  Given a 30-day window of install failures
  When  we count INSTALLATION_FAILED events per CSP / zone
  Then  the count is unchanged
        (enriching categorisation; not adding or removing events)
REGRESSION-6 (A6 row 6): EsInstallReportedFailed legacy fields stay validated
  Given the 10 existing fields on EsInstallReportedFailed
  When  CL receives the event
  Then  the existing @NotBlank / @NotNull validations fire exactly as today
  And   the 4 new fields are validated as Optional (per OS §7.2)
REGRESSION-7 (A6 row 7): TasInstallTerminal path unchanged
  Given Quality OS subscribes to TasInstallTerminal
  When  TAS emits it (alongside EsInstallReportedFailed)
  Then  the TasInstallTerminal payload is unchanged
        (extending it to carry the 4 fields is a follow-up item if Quality OS needs it)
