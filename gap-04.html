Wiom · Change Spec · v1.0 · PM deliverable · GAP-04

DAS supply-side events for single-CSP zones

DAS already detects single-provider continuity mode (RoutingEngineServiceImpl.detectMode returns RoutingMode.CONTINUITY when eligibleCount ≤ 1). It also has the listener-side outbox plumbing wired for SingleProviderContinuityActive and ZoneSupplyDeficitSignal. What's missing: the eventPublisher.publishEvent(...) calls that bridge detection to emission, and the P46BreachByContinuity event isn't wired in DAS at all (its event record + listener don't exist on the DAS side, even though Capacity OS has the receiver). End result: Capacity OS waits for signals that never arrive; supply-deficit resolution loop is dark.

Author: Ashish Raj  ·  Reviewer: Engineering  ·  Tier: Light
Tier: Light — A1, A2, A5, A6, A8, B5. Add 3 emit-site calls + 1 missing event class + 1 missing listener method.
Rows: Required — every row filled or marked N/A with a reason.

What is changing?
DAS emits the 3 OS-prescribed supply-side events when continuity mode is entered / breached: SINGLE_PROVIDER_CONTINUITY_ACTIVE, ZONE_SUPPLY_DEFICIT_SIGNAL, P46_BREACH_BY_CONTINUITY.
What triggered it?
DAS OS §3.14 (BDN-DA-02 + BDN-CA-02) prescribes these signals; DAS detects the mode and Capacity OS has the receivers, but no events flow. Supply-deficit resolution loop never closes.
Blast radius
DAS RoutingEngineServiceImpl (continuity-mode entry path + P46 breach path) · DAS EventSender (1 new listener method) · DAS shared-libs / outbound event package (1 new P46BreachByContinuity record) · No Capacity OS change (receivers already built).
Reversible?
Yes — emissions can be wrapped in a feature flag if needed; rollback = stop emitting.
Money / PII / migration?
No / No / No.
OS impact / sign-off?
No D&A OS amendment — implementing what §3.14 already prescribes. ESR doc update for confirming the event-schema registration (events may already be registered there from earlier work).

A2. Why This Change WHAT

What is expected: A short problem statement.
All rows required
QuestionAnswer
What's wrong with the current behaviour?DAS OS §3.14 prescribes 3 supply-side events for continuity mode. DAS has the detection wired (RoutingEngineServiceImpl.detectMode() at line 233 returns RoutingMode.CONTINUITY when there's exactly 1 eligible CSP). DAS also has the listener-side outbox plumbing for 2 of the 3 events (EventSender.onSingleProviderContinuityActive line 55 and onZoneSupplyDeficitSignal line 62 — both @TransactionalEventListeners that schedule to outbox). What's missing on the DAS side: (a) no eventPublisher.publishEvent(...) calls anywhere in DAS for these 2 events — the bridge between detection and emission is absent; (b) the P46BreachByContinuity event record doesn't exist in DAS outbound and there's no listener for it. Capacity OS already has the inbound endpoints (POST /p46-breach-by-continuity at line 145 and POST /zone-supply-deficit-signal at line 168 of its InboundEventController), but they receive zero events in prod.
Who experiences it?Customers in single-CSP zones — supply deficit goes unresolved; Capacity OS never receives the signal to onboard new CSPs. Ops trying to find under-served zones — no programmatic signal, must mine DB state. Auditors looking for the legal P46 breach trail — no audit signal when DAS allows enforcement-triggered over-cap reassignments.
Cost of leaving it as-is?The OS-prescribed supply-deficit-response loop doesn't close. Customers in deficit zones stay un-served indefinitely. P46 breaches during continuity (the only legal way to exceed P46 per INV-DAO-17) have no audit trail.

Atomic deltas

What changesBeforeAfterWhy
DAS continuity-mode entry emit site RoutingEngineServiceImpl.detectMode() returns RoutingMode.CONTINUITY but no events are published. The caller (route handler at line 56) acts on the mode without firing the signal. At the continuity-mode entry transition (mode flips from NORMAL to CONTINUITY for a zone), publish both SingleProviderContinuityActive and ZoneSupplyDeficitSignal via eventPublisher.publishEvent(...). The existing listener-side wiring at EventSender picks them up and schedules to outbox. The bridge between detection and emission. Listeners already exist; just need the publish calls.
DAS continuity-safety-floor-kill emit site At line 56-65 of RoutingEngineServiceImpl, when continuity mode + CSP is SUSPENDED/FPV_FLAGGED, allocation is killed and the path returns. No supply-deficit signal is emitted. Publish ZoneSupplyDeficitSignal at this site too (the OS explicitly mentions emit on safety-floor kill, L307: "KILL continuity → allocation = ZERO; emit ZONE_SUPPLY_DEFICIT_SIGNAL"). Capacity OS needs the signal regardless of whether continuity was entered cleanly or killed for safety.
New event record — P46BreachByContinuity in DAS outbound Doesn't exist in DAS outbound package. Capacity OS has the inbound version (services/csp-capacity-coverage-service/.../P46BreachByContinuity.java) and shared-libs has the contract record (services/shared-libs/csp-event-contracts/.../P46BreachByContinuity.java) — but DAS has no outbound class. Add the outbound record in DAS at services/csp-demand-allocation-service/.../domain/event/outbound/P46BreachByContinuity.java mirroring the shared-libs contract. Fields: (eventId, csp_id, zone_id, breach_amount, breach_reason, source_csp_id, timestamp). DAS needs its own outbound record to publish via the existing listener pattern.
New EventSender listener method — onP46BreachByContinuity Doesn't exist. EventSender only listens for SingleProviderContinuityActive and ZoneSupplyDeficitSignal. Add a @TransactionalEventListener method onP46BreachByContinuity that schedules to outbox (same pattern as the other two — partition key = zone_id). Outbox plumbing for the 3rd event.
DAS P46 enforcement-breach emit site At the P46 continuity exception in RoutingEngineServiceImpl (the path that allows over-cap when enforcement-triggered — per OS L380-382), no audit signal is emitted. Publish P46BreachByContinuity at this site via eventPublisher.publishEvent(...) with breach_amount + source_csp_id from the enforcement context. The new listener at EventSender picks it up and schedules to outbox. Audit trail for the legal P46 breach (only legal mechanism to exceed P46 per INV-DAO-17).
Out of scope: Capacity OS's response logic when it receives these signals (it owns onboarding new CSPs — that's its own change spec if needed); modifications to the existing continuity-mode detection logic at RoutingEngineServiceImpl.detectMode() (detection is correct, just doesn't emit); multi-CSP-zone routing behaviour (unchanged); Visibility OS dashboard wiring for SINGLE_PROVIDER_CONTINUITY_ACTIVE (Visibility OS owns its own consumer).

Business logic

LOGIC-1: Zone goes from multi-CSP to single-CSP → both entry signals fire
  Real-world: a zone that previously had 2+ eligible CSPs drops to 1
  (the other CSP exited / got suspended / got FPV-flagged). DAS routing flips to
  continuity mode; Capacity OS must be told both pieces of news (continuity active +
  supply deficit).

  Given a zone where the eligible-CSP count drops from 2 to 1
  When  DAS routing runs and detectMode() transitions to RoutingMode.CONTINUITY
  Then  DAS publishes SingleProviderContinuityActive
        (payload: zone_id, csp_id, cap_ratio, reason, started_at)
  And   DAS publishes ZoneSupplyDeficitSignal
        (payload: zone_id, csp_id, severity)
  And   both land in the DAS outbox via the existing @TransactionalEventListener wiring
  And   Capacity OS receives ZoneSupplyDeficitSignal at POST /zone-supply-deficit-signal

  Verify:
    • DAS outbox — csp_demand_allocation_service.outbox_record
        WHERE created_at > <test start> AND payload references <test zone_id>
        → expect 2 rows: one record_type ending in SingleProviderContinuityActive, one ending in ZoneSupplyDeficitSignal
        → both with status = 'DELIVERED'
    • Capacity OS — verify the POST /zone-supply-deficit-signal handler logged receipt
        (check capacity-service logs or processed-event table for the zone_id)
LOGIC-2: Continuity safety-floor kill — supply-deficit still fires
  Real-world: the zone has a single CSP and that CSP is SUSPENDED or FPV-flagged.
  DAS can't allocate at all; allocation = zero. Capacity OS still needs the supply-deficit signal.

  Given a zone in continuity mode where the lone CSP is SUSPENDED or FPV_FLAGGED
  When  DAS routing runs and hits the safety-floor branch
        (line 56-65 of RoutingEngineServiceImpl)
  Then  allocation = ZERO (existing behaviour, unchanged)
  And   ZoneSupplyDeficitSignal is published
        (the OS explicitly mentions emit here at L307)
  And   Capacity OS receives the signal

  Verify:
    • DAS DB — csp_demand_allocation_service.connection_allocations
        → no new row for this attempt (allocation = zero, existing behaviour)
    • DAS outbox — 1 new ZoneSupplyDeficitSignal row, status = 'DELIVERED'
LOGIC-3: P46 breach during enforcement-triggered reassignment
  Real-world: the source CSP is suspended; an enforcement-triggered reassignment
  pushes the lone CSP over their P46 cap. This is the OS-sanctioned legal breach path.

  Given a zone in continuity mode where the source CSP is SUSPENDED / exited
        AND an enforcement-triggered reassignment would push the lone CSP over P46
  When  DAS routing allows the over-cap allocation (per OS L380-382)
  Then  the allocation succeeds (existing behaviour, unchanged — only the legal mechanism)
  And   DAS publishes P46BreachByContinuity
        (payload: csp_id, zone_id, breach_amount, breach_reason=ENFORCEMENT_REALLOCATION,
         source_csp_id, timestamp)
  And   Capacity OS receives the event at POST /p46-breach-by-continuity

  Verify:
    • DAS DB — connection_allocations → over-cap allocation row created
    • DAS outbox — 1 new P46BreachByContinuity row, status = 'DELIVERED'
        → payload contains breach_reason = 'ENFORCEMENT_REALLOCATION' + source_csp_id
    • Capacity OS — POST /p46-breach-by-continuity handler logged receipt
LOGIC-4 (negative): No emission for multi-CSP zones
  Real-world: a healthy zone with 2+ eligible CSPs runs in NORMAL mode and must
  not emit any of the continuity-mode signals.

  Given a zone with 2+ eligible CSPs
  When  DAS routing runs
  Then  detectMode() returns NORMAL (existing behaviour, unchanged)
  And   NO SingleProviderContinuityActive is published
  And   NO ZoneSupplyDeficitSignal is published
  And   NO P46BreachByContinuity is published

  Verify:
    • DAS outbox — csp_demand_allocation_service.outbox_record
        WHERE created_at > <test start> AND payload references <test zone_id>
        AND record_type matches any of the 3 continuity events
        → expect 0 rows
LOGIC-5 (negative): No P46 breach signal for non-enforcement over-cap attempts
  Real-world: if a regular allocation would push a CSP over P46 (no continuity
  mode involved), DAS rejects normally. The breach event fires only on the OS-sanctioned path.

  Given a non-continuity zone with a CSP at P46
  When  an ordinary allocation would push them over P46
  Then  DAS rejects the allocation (existing behaviour)
  And   NO P46BreachByContinuity is published
        (the event fires only on the OS-sanctioned breach path)

  Verify:
    • DAS DB — connection_allocations → no allocation row (rejected)
    • DAS outbox — no P46BreachByContinuity row created

Use & edge cases

EDGE-1: Zone toggles between NORMAL and CONTINUITY within minutes
  Real-world: exposures shift fast in some zones — the eligible-CSP count can
  bounce between 1 and 2. Each NORMAL → CONTINUITY transition emits; exit is silent.

  Given a zone that toggles between 1 and 2 eligible CSPs as exposures change
  When  the mode flips multiple times in a short window
  Then  each NORMAL → CONTINUITY transition publishes the pair
  And   each CONTINUITY → NORMAL transition does NOT publish anything in this item
        (exit signal is out of scope per A6 row 6)
  And   no debouncing is applied at PM level
        (engineering may add debouncing as an implementation choice)

  Verify:
    • DAS outbox — count entry-pair rows for the test zone across the window
        → expect 1 pair (SingleProviderContinuityActive + ZoneSupplyDeficitSignal) per NORMAL→CONTINUITY transition
        → 0 rows on any CONTINUITY → NORMAL transition
EDGE-2: Zone enters continuity AND the lone CSP is already at P46
  Real-world: double-bind — zone goes single-CSP and that CSP is already at cap.
  Entry signals fire first; the breach signal fires when the over-cap allocation is allowed.

  Given a zone entering continuity where the lone CSP is already at P46 cap
  When  the next allocation would breach P46 via the enforcement path
  Then  continuity-entry signals fire first
        (SingleProviderContinuityActive + ZoneSupplyDeficitSignal)
  And   P46BreachByContinuity fires when the over-cap allocation is allowed
  And   Capacity OS receives all 3 events (ordering: entry signals before breach)

  Verify:
    • DAS outbox — 3 rows in order:
        1. SingleProviderContinuityActive
        2. ZoneSupplyDeficitSignal
        3. P46BreachByContinuity
        (created_at timestamps strictly ascending)
    • Capacity OS — 3 inbound events recorded for the zone in the same order
EDGE-3: Outbox delivery fails (Capacity OS briefly down)
  Real-world: Capacity OS returns 5xx for a few minutes. The DAS outbox retry
  handles redelivery — no new retry logic added by this item.

  Given any of the 3 events scheduled to the DAS outbox
  When  initial delivery fails (HTTP 5xx from Capacity OS)
  Then  the existing outbox retry logic handles redelivery
        (existing behaviour for all DAS outbound events — no new retry logic in this item)
  And   eventual successful delivery still reaches Capacity OS

  Verify:
    • DAS outbox — outbox_record row transitions from 'FAILED' → 'DELIVERED' across retries
    • Capacity OS — eventual receipt confirmed in capacity-service logs / processed-event table
