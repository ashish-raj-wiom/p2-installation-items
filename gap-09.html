Wiom · Change Spec · v1.0 · PM deliverable · GAP-09

Timeline misses the first update — "new booking allotted"

When a new connection is allotted to a CSP, the partner app's Updates timeline does not show this event. The timeline only starts surfacing entries from the slot-proposal moment onwards. The very first action the partner needs to know about — "you have a new booking to act on" — is silently missing. This is a backend gap: the audit table that the timeline endpoint reads from never gets a row written for the initial allotment, even though the partner's update version counter does jump forward at that moment. This spec writes the missing first row so the timeline begins where it should.

Author: Ashish Raj  ·  Reviewer: TAS Engineering  ·  Tier: Light
Scope: backend-only. One audit-row write at booking-allotment time + a display copy for the new entry. No app changes (the existing timeline endpoint will just start carrying this entry like any other). No state-machine change.

Quick Check

7-line triage — read this before the rest.
What is changing?
At the moment a new install booking is allotted to a CSP, the backend writes a row into the timeline audit table (the one the partner-facing timeline endpoint already reads from). The partner app's Updates section then shows "new booking allotted" as the first entry, alongside the existing entries for slot proposal, customer confirmation, technician assignment, install-day reminder, and so on.
What triggered it?
QA on staging — the partner timeline begins at "Slot proposed" instead of "Booking allotted." The PM checked the API response: the unseen-count counter on the booking sits at version 5 but the timeline returns only 4 entries (versions 2, 3, 4, 5). Version 1 — the booking-allotment moment — is missing from the table the API reads from.
Where the data lives
The timeline endpoint reads from a table called install_attention_event_log on the partner-side backend (TAS). Each row in this table is one "update" the partner needs to see. Today, when a candidate is created (booking allotted), the backend bumps the partner-facing version counter on the booking row but does not write a corresponding audit row for that bump. So when the partner app fetches the timeline, version 1 has nothing to show.
Who is affected?
Partners — their Updates section starts mid-flow ("slot proposed") with no preceding "you've got a booking" entry, which is the most important update for them to act on. Ops — debugging customer-partner timeline mismatches becomes harder when the initial event is invisible. Customers — indirectly, because partner confusion at the lead step delays bookings.
Out of scope
Push notifications. Partner-app UI styling. Counter semantics (the unseen-count logic itself is fine — only the audit row is missing). Other "missing-entry" issues on the timeline if any.
Risk to flag
The fix is a single write at candidate-creation time. The risk is double-counting if the existing version counter is not reset to start from a clean baseline as part of this change. The TAS engineer should confirm whether the counter should reset to 0 and be advanced by the new write, or stay at 1 and just have a back-fill row added. Either approach works; the team should pick one and stay consistent.
What success looks like
When the partner opens the Updates section on a newly-allotted booking, the very first entry says "new booking allotted to you" (with Hindi and English copy), with timestamp matching the moment the booking was allotted. All subsequent updates (slot proposed, customer confirmed, etc.) follow normally, with version numbers consistent with the unseen-count counter.

A2. Why This Change WHAT

The problem in one paragraph

When a connection gets allotted to a CSP, that's the most important update the partner needs to see — it's the moment they have something to act on. The partner app surfaces this kind of information in its Updates timeline, which is driven by a TAS endpoint that reads from an audit table. Today, that audit table has no row for the allotment moment. The partner's update counter does bump (so the "unseen" badge is correct), but when the partner taps in to read the actual update, the first entry they see is the slot proposal — which happens later, after they've already acted. The initial trigger is invisible.

What the API returns today (verbatim)

Capture from staging on 2026-06-17 — the partner-side timeline endpoint returns:

"current_version": 5,
"acked_version": 5,
"unseen_count": 0,
"total_elements": 4,            // ← only 4 entries despite version count of 5
"entries": [
  { "version": 5, "reason_code": "INSTALL_DAY_REMINDER",      ... },
  { "version": 4, "reason_code": "Technician assigned: 305",  ... },
  { "version": 3, "reason_code": "Customer confirmed slot 1", ... },
  { "version": 2, "reason_code": "Slot proposed",             ... }
  // version 1 — missing
]

Five versions exist on the booking row's counter; only four show up in the timeline. The missing one is the first: the booking-allotment moment.

Who experiences it

  • Partners (CSPs, technicians) — open the Updates section, the first entry is "selected time is sent" (slot proposal). They had to act before that — they proposed the slot in the first place — but no entry tells them why the booking landed on their app.
  • Ops — when investigating a partner-facing complaint, the audit trail is missing the originating event. Have to cross-reference with the candidate state log (a different table) to reconstruct.
  • Customers — indirectly affected when partner confusion at the lead step delays the booking flow.

Cost of leaving it as-is

The partner timeline is presented as a complete history of "what's happening with this booking on your side." Missing the first step makes the feature feel incomplete and undermines confidence in the timeline as a single source of truth. As more partners come onto the app, the gap shows up more and gets harder to explain away.

A5. The Delta WHAT

What is expected: One row per change, in business terms.
What changesTodayAfter this changeWhy
Write the first timeline row at booking-allotment time When a candidate (install booking) is created on the partner side, the booking's "latest update version" counter starts at 1, but no corresponding row gets written to the timeline audit table. So when the partner app fetches the timeline, the first row it sees is from the next update (slot proposal), at version 2. At the moment of candidate creation, a row is written into the timeline audit table at version 1. The row carries the same shape as any other timeline row: an occurrence time (= the allotment moment), the trigger reason ("booking allotted"), and the display copy (see next row). The audit table is the single source of truth that the partner app reads from. If a partner-visible update doesn't have a row here, it's invisible. The version counter being correct without the row being written is the actual gap.
Display copy for the new entry No copy exists for this entry because the entry doesn't exist. The new row carries display text in English and Hindi, matching the style of existing timeline entries. Suggested copy:
· title_en: "New booking allotted to you"
· title_hi: "आपको एक नया कनेक्शन मिला है"
· subtitle_en: "Propose a slot to the customer"
· subtitle_hi: "ग्राहक को इंस्टॉलेशन का समय भेजें"
· category: ALERT (since this is the first action-driving entry)
· icon: a bell or new-booking icon (final choice with Design)		 The partner needs to know what's happened and what to do next. The subtitle tells them the next action; the ALERT category surfaces it visually as actionable rather than informational.
Update the timeline API if any filter excludes version 1 To be confirmed by the TAS engineer: does the timeline endpoint filter rows by version range, or does it simply return whatever exists in the audit table for this booking? The data shows it returns whatever exists — so once the row is written, it should appear. verify If the endpoint already returns all rows regardless of version (most likely), then once the v1 row is written, the partner timeline will start showing it. If a filter exists that drops it, the filter is updated to include v1. Defensive — confirms that no other code path silently drops version 1 once the row is present.
Counter alignment — pick one of two consistent paths Today the booking row's counter starts at 1 but no row backs that 1. There are two consistent ways forward; the team should pick one. Option A: the booking row's counter starts at 0; the new write at allotment-time advances it to 1 (and writes the v1 row). Subsequent updates advance normally to 2, 3, 4. This keeps "counter value = number of rows in the audit table" — easiest invariant to reason about.

Option B: the booking row's counter keeps starting at 1; the new write doesn't change the counter, just back-fills the missing v1 row. Subsequent updates continue from 2 as today. This is a one-line change but leaves the "1 row implicit, written from row 2 onward" mental model — slightly weirder.

Recommend Option A — easier invariant, no future surprises. TAS engineer to confirm whichever approach they pick stays consistent across the affected callsites.		 Either approach delivers the partner-visible outcome (timeline starts at allotment). Option A is cleaner; Option B is smaller. Picking one explicitly avoids the bug coming back via inconsistency.
What this gap is — and isn't. This is purely a missing audit row. The partner-app code, the timeline endpoint, the audit-table schema, the version-counter logic — all already exist and work. The only thing missing is the write at the allotment moment. One small backend change unblocks the partner-visible outcome.

The flow at a high level

  1. A booking is allotted to a CSP (DAS picks the CSP → notifies the partner side).
  2. The partner side creates a candidate (the install-side record of "we have this booking to act on"). Today this is where the audit row is missing. After the fix, this is where the new row gets written.
  3. The partner gets a notification (push / in-app) and opens the booking. The Updates section now shows "new booking allotted" as the first entry.
  4. The partner proposes a slot → new row added at version 2 (same as today).
  5. Customer confirms → version 3. Technician assigned → version 4. Install-day reminder → version 5. (All unchanged.)

Part B

HOW — Detailing

What success looks like — described as scenarios.

A QA / engineering team will turn these into test cases at build time.

B5. What success looks like HOW

What is expected: Scenarios in plain English. Each one describes a real situation and what should happen.

Scenario 1 — A new booking lands on the partner side

Routing assigns a new connection to CSP X. The partner side creates a candidate for the booking.

What should happen:

A row is written into the timeline audit table at version 1, with reason_code = BOOKING_ALLOTTED, occurrence time equal to the moment the candidate was created, and the new English + Hindi display copy. The partner's update counter shows 1 unseen update. When the partner opens the Updates section, the first (and only, at this point) entry says "New booking allotted to you" with the matching subtitle.

Scenario 2 — Partner proposes a slot after seeing the allotment

The partner reads the "new booking allotted" entry, then proposes a slot to the customer (same flow as today).

What should happen:

A second audit row is written at version 2 with reason_code = "Slot proposed", exactly as today. The partner's Updates section now shows two entries — slot proposed on top (newest first), booking allotted below. Counter shows 2 latest, with the acked-version following the partner's behaviour.

Scenario 3 — A booking in flight when this change deploys

Some bookings were already in flight before this change — their candidates exist on the partner side, but the v1 row was never written for them.

What should happen:

Two acceptable approaches; the team should pick one:
(a) Leave existing bookings as they are — they continue to show timelines starting from v2 (the existing state). Only newly allotted bookings (post-deploy) get the v1 row.
(b) Back-fill: write a v1 row for every active candidate that's missing one, with the candidate's created_at as the occurrence time and "BOOKING_ALLOTTED" as the reason code.
Recommend (a) — back-fills carry edge-case risk (counter alignment) and the gap is small for partners with in-flight bookings. TAS engineer to confirm.

Scenario 4 — Partner re-fetches the timeline after the v1 row exists

Partner-app refresh, pagination, or background sync hits the timeline endpoint again.

What should happen:

The endpoint returns the same rows it would return on first load — v1 (booking allotted), v2 (slot proposed), and so on. Pagination and ordering work normally. No duplicate writes (the v1 row is written once at candidate creation, not on every fetch).
