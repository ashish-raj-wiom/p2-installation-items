[Change Name] — Change Specification

For modifications to an existing feature's behaviour or logic (the change goes PM → Engineering). A modification is a diff, not a feature — so this spec is built around current → desired → delta, and protects what must stay the same. Business behaviour only; engineering owns implementation. If you are building something new, use the Product Solution Spec instead. If the change is UI-only with no backend dependency, it is a design PR — no spec needed.

Author: PM  ·  Reviewer: Engineering  ·  Governs tiering: Lead PM
Tiers: Light A1, A2, A5, A6, A8, B5 — a contained logic tweak (A8 is always declared). Full all sections — touches multiple workflows, state, or money. Lead PM picks the tier at triage; mark it in the Quick Check.
Rows: Required fill or mark N/A with reason · Example illustrative — keep what fits, delete the rest. Worked examples stay visible (yellow).

Part A

WHAT — The Change

The PM's decisions: why we are changing this, what it does today, what it should do, and the precise delta. Stable across implementation revisions.

Authored by the PM. Changes here trigger re-review.

A1. Metadata WHAT

What is expected: Title, owner, status, version, and a link to the feature's original PRD / OS so the reviewer can see the baseline being changed.
All rows required

A2. Why This Change WHAT

What is expected: A short problem statement so the reader understands the change is solving a real problem, not a preference. Observable trigger, who is affected, cost of leaving it. Two or three lines — keep it light, but never skip it.
All rows required
QuestionAnswer
What's wrong with the current behaviour?[Observable problem]
Who experiences it?[Affected actor]
Cost of leaving it as-is?[Why it's worth a change]
Worked example
Autopay-failure grace window
QuestionAnswer
What's wrong?When an autopay mandate fails on validity-end day, service is suspended immediately. Most failures are transient (bank-side) and clear within hours, but the customer is already offline and treats it as a broken promise.
Who?Autopay customers whose mandate fails on the due date (~X% of autopay base/month).
Cost of leaving it?Avoidable churn and trust loss on customers who had every intention of paying; ops tickets to manually restore.

A3. Current Behaviour WHAT

What is expected: How the system observably behaves today, for the slice you are about to change. Describe what an observer sees — inputs, decisions, outputs — not how it is coded. The current code is available; you are summarising its behaviour, not its structure.
Tip: Write it as "Given X, the system does Y." If you find yourself naming tables, services, or functions, you've slipped into implementation — pull back to observable behaviour.
Example
Trigger / conditionObservable behaviour today
Autopay mandate fails on validity-end dayService is suspended at the moment the validity window ends; customer goes offline immediately. A single retry is attempted at suspension; no grace period.
Customer recharges manually after suspensionService restores within the normal provisioning window.

A4. Desired Behaviour WHAT

What is expected: The same observable slice, after the change. Mirror A3's structure so the reader can read them side by side.
Example
Trigger / conditionDesired observable behaviour
Autopay mandate fails on validity-end dayService continues for a grace window (default 24h). The customer is told payment failed and that service continues briefly while it is retried. Retries run across the window.
Payment succeeds within the grace windowValidity is recharged as normal; no suspension ever occurs; the customer is told they're sorted.
Grace window elapses with no successful paymentService is suspended as it is today; customer told the grace period ended.

A5. The Delta WHAT

What is expected: The heart of the spec. One row per rule, workflow step, output, or parameter that changes. Each row: what it does now → what it should do → why. This table is what engineering builds against and what test cases are generated from.
A4 or A5? A single picture of the result the reader can hold in their head → A4 (Desired behaviour). The itemised list of differences, one change per row → A5. A4 is for comprehension; A5 is for build and test.

A6. Must-Not-Change — Regression Guard GUARD

What is expected: The behaviours adjacent to this change that must survive untouched. This is how we move fast without breaking trust. Scope it to what a reasonable engineer might fear breaking — not an exhaustive inventory of the system. Each line here becomes a regression assertion in B5.
Reviewer note: sufficiency of this list is judged by the lead PM. Too short and a real risk is unguarded; exhaustive and it becomes ritual. Aim for the handful of behaviours genuinely in the blast radius.
Example rows
Adjacent behaviour that must not changeWhy it's in the blast radius
Manual (non-autopay) recharge → suspension timing is unchanged.Shares the suspension code path; easy to catch in the change.
Non-autopay customers see no grace window and no new messaging.The new behaviour must not leak to customers it wasn't designed for.
Validity-end date for successful autopay (no failure) is unchanged.The happy path must be byte-for-byte as before.

A7. Rules, Invariants & Edge Cases Affected WHAT

What is expected: Business rules the change adds or alters; invariants — truths that must always hold once the change ships (e.g. "a customer is in exactly one service state at any moment"); and the new edge cases the change introduces. For each edge: the condition and the intended business outcome (not the handling mechanism). Everything declared here must be verified in B5.
A6 or A7? A behaviour that must be preserved unchanged → A6. A rule or invariant that changes or is newly introduced, or a new edge → A7. They are mirror images.
Example rows

A7.1 Rules & invariants (must always hold)

Rule / invariantStatement
INV — service-state exclusivityAt any moment a customer is in exactly one service state: active, in-grace, or suspended — never two at once.
INV — settlement integrityA customer kept live by a grace window is not treated as paid for settlement until an actual payment succeeds.
RULE — single open windowA customer can have at most one open grace window at a time.

A7.2 Edge cases

Edge / conditionIntended business outcome
Payment succeeds in the final minute of the grace windowTreated as success; no suspension; normal recharge.
Customer manually recharges while a grace window is openManual payment wins; grace window closes; service continues seamlessly.
Mandate fails again on the next cycle while still inside a grace-extended period[Decision needed — define before build]

A8. OS Impact & Sign-off GATE

What is expected: A modification often ripples into an OS the PM does not own — its behaviour, its cross-OS contract, or its SPR parameters. Declare every OS this change touches, the amendment, the amendment owner you consulted, and whether they have signed off. This mirrors the Product Solution Spec's A4 (OS ownership), A9 (cross-OS impact) and B3.2 (SPR amendment). A row marked impacted with sign-off still Pending blocks the change from shipping — this is the accountability gate.
How to declare: list the OSes plausibly in the blast radius and give each an explicit Yes/No — silent omission is how cross-team incidents happen. "No" rows need no owner; every "Yes" needs a consulted owner (not merely assigned) and a sign-off status. If the change touches no OS at all, keep a single row stating so and why.

Part B

HOW — Detailing

The supporting detail engineering needs to build and test the delta precisely. Light tier may skip B1–B4 and keep only B5.

Still business behaviour — diagrams describe logic and outcomes, never architecture.

B5. Acceptance Criteria — Verification Layer HOW

What is expected: The robust verification layer that proves the generated code is correct and nothing adjacent broke. Given / When / Then criteria must exhaustively cover four classes, plus regression. A change is not verified until every item in every class has at least one block.
1. Business logic — every rule added or changed (A5 delta, A7.1). Happy and negative paths.
2. Computation & calculation — every value the change computes or alters (amounts, durations, counts, thresholds, derived values). Tested at normal values and at boundaries: zero, maximum, rounding, off-by-one, window expiry.
3. Invariants — every "must always hold" truth (A7.1). Asserted as conditions that hold across all paths, including failure paths.
4. Use & edge cases — every happy path, negative path, and edge (A7.2); every new / changed branch (B1) and transition (B2).
5. Regression — a REGRESSION block for every A6 guard line.
Why this matters: code is AI-generated; review is human. B5 is the contract the generated code is checked against. A class left uncovered is a class no one verified — that is exactly where "moved fast, broke trust" happens. Label every block with its class so coverage is auditable.
Example blocks
LOGIC_01 (business logic · happy): Grace absorbs a transient failure
Given an autopay customer whose mandate fails on validity-end day
When a retry succeeds within AUTOPAY_GRACE_HOURS
Then service is never suspended
And validity is recharged as on a normal cycle
LOGIC_02 (business logic · negative): Grace window elapses
Given an autopay customer in an open grace window
When no payment succeeds before the window ends
Then service is suspended
And the customer is told the grace period has ended
COMPUTE_01 (computation · boundary): Window expiry is exact
Given a grace window opened at time T with AUTOPAY_GRACE_HOURS = 24
When the clock reaches exactly T + 24h with no successful payment
Then the window is treated as elapsed and service is suspended
And a payment arriving one second after T + 24h does not prevent suspension
COMPUTE_02 (computation · zero / config): Zero-hour grace
Given AUTOPAY_GRACE_HOURS is set to 0
When an autopay mandate fails
Then behaviour is identical to the pre-change immediate suspension
And no grace state is ever entered
INVARIANT_01 (from A7.1): Service-state exclusivity
Given any autopay customer at any moment, including mid-retry
Then the customer is in exactly one service state (active / in-grace / suspended)
And never in two states at once
INVARIANT_02 (from A7.1): Settlement integrity
Given a customer kept live by a grace window
Then at no point is the customer treated as paid for settlement
Until an actual payment succeeds
REGRESSION_01 (guard · from A6): Non-autopay unaffected
Given a non-autopay customer whose validity lapses
When the validity window ends
Then suspension timing is exactly as before the change
And no grace messaging is shown

Author rule: N/A on a conditional section needs a one-line reason. Every A6 guard maps to a B5 REGRESSION block. Every A7.1 invariant and every changed calculation maps to a B5 block. Every A8 OS marked impacted is consulted, not merely assigned.

Reviewer rule (engineering): Read Quick Check, then A5 (delta), A6 (guard), A8 (OS impact), and the B5 coverage matrix in full. Reject if: A5 mixes in implementation; A6 is empty / hand-wavy; any A8 "Yes" has sign-off Pending; or the B5 coverage matrix has any class not "all covered" — a computation with no boundary block, an A7.1 invariant with no INVARIANT block, an edge / branch / transition with no block, or an A6 line with no REGRESSION block.

Out-of-scope for this spec: API contracts, event/payload schemas, database design, concurrency / locking, retry / backoff mechanics, monitoring thresholds, alert routing, dedup keys, pixel-level UI and exact copy. Engineering and design own these.

What this spec is — and isn't: The canonical articulation of how an existing behaviour should change. Not a code-generation contract; engineering decides architecture and produces its own downstream artefacts from this spec.
