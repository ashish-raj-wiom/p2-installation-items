Wiom · Change Spec · v1.0 · PM deliverable · GAP-01

Bifurcate booking cancellations by source (customer vs system)

CL already carries the actor-tag (deactivationSource) on its outbound signal, but TAS's install ClDeactivationInitiated record deserializes only 4 of 14 fields. The bifurcation field is dropped at the HTTP boundary; every cancellation lands in CANCELLED_BY_UPSTREAM. Fix is in TAS: extend the DTO, branch on deactivationSource. No CL OS amendment; no new terminal states.

Author: Ashish Raj  ·  Reviewer: Engineering  ·  Tier: Light
Tier: Light — A1, A2, A5, A6, A8, B5. Contained logic change at the wire boundary.
Rows: Required — every row filled or marked N/A with a reason.

Quick Check

7-line triage. Filled last, after the body is complete.
What is changing?
Stop dropping the cancellation actor-tag at the CL → TAS boundary. Cancellations land in the correct existing terminal state (CANCELLED_BY_CUSTOMER vs CANCELLED_BY_UPSTREAM).
What triggered it?
Prod data — every recent install cancellation lands in CANCELLED_BY_UPSTREAM with a generic reason; the CANCELLED_BY_CUSTOMER branch is dead code in prod despite existing in spec + state machine.
Blast radius
TAS install ClDeactivationInitiated DTO · TAS install handler · ES PRD wording. CL already correct (verified — emits 14 fields including deactivationSource).
Reversible?
Yes — additive field handling; rollback = ignore the field.
Money / PII / migration?
No / No / No (no retroactive re-classification of historical rows).
OS impact / sign-off?
No CL OS amendment — CL outbound contract already carries deactivationSource and deactivationReason. ES PRD documentation update only — sign-off Pending.

A2. Why This Change WHAT

What is expected: A short problem statement. Observable trigger, who is affected, cost of leaving it.
All rows required
QuestionAnswer
What's wrong with the current behaviour?CL service correctly tags every CL_DEACTIVATION_INITIATED outbound signal with deactivationSource — "USER_INITIATED" on customer-driven cancels, "SYSTEM_INITIATED" on system-driven (and CL carries deactivationReason as a passthrough cause string). The install TAS record ClDeactivationInitiated only deserializes 4 of 14 fields (eventId, correlationId, causationId, connectionId) — deactivationSource, deactivationReason, and 8 others are silently dropped at the HTTP boundary. The install handler then hard-codes sourceOs = "CL_DEACTIVATION_INITIATED" + reasonCode = "DEACTIVATION" and always calls cancelByUpstream(...).
Who experiences it?ES candidate analytics — the CANCELLED_BY_CUSTOMER branch is dead code in prod (state + method exist but the path is never hit). Quality OS / Enforcement OS pattern attribution — system-cancels and customer-cancels collapse into one bucket. Ops investigating cancellation patterns can't tell which type spiked.
Cost of leaving it as-is?100 % of install cancellations are mis-routed at TAS today. The spec-mandated bifurcation exists end-to-end except for the wire-deserialization gap.

B5. Acceptance Criteria — Verification Layer HOW

What is expected: Given / When / Then blocks covering business logic, computation, invariants, use / edge cases, plus a REGRESSION block for every A6 guard. Plus a coverage matrix that reads "all covered" on every class.

Business logic

LOGIC-1: Customer cancels their booking → task marked "cancelled by customer"
  Real-world: a customer taps Cancel in the Customer App.

  Given a cancellation arrives at TAS install with source = "USER_INITIATED"
        (the actor-tag CL stamps on customer-driven cancels)
  When  the handler processes the event
  Then  the install candidate is cancelled via cancelByCustomer(candidateId, eventId, correlationId)
  And   the candidate lands in CANCELLED_BY_CUSTOMER (the OS-defined terminal for this case)
LOGIC-2: System cancels the booking → task marked "cancelled upstream" with the real reason
  Real-world: any non-customer cancel — support agent in CRM, Wiom timeout,
  Exit OS, Enforcement OS, etc.

  Given a cancellation arrives at TAS install with source = "SYSTEM_INITIATED"
        and deactivationReason = "<the actual upstream cause>"
  When  the handler processes the event
  Then  the install candidate is cancelled via cancelByUpstream(
            candidateId, "CL_DEACTIVATION_INITIATED",
            <the actual deactivationReason from the event>,
            eventId, correlationId
        )
  And   the candidate lands in CANCELLED_BY_UPSTREAM
  And   the candidate's reasonCode preserves the actual upstream cause
        (no longer hard-coded "DEACTIVATION")
LOGIC-3: A booking with multiple active install tasks → all get cancelled together
  Real-world: a single connection sometimes has more than one active install task
  (e.g. after a retry). The cancel must clean up all of them.

  Given a cancellation arrives
  And   the connection has multiple active install candidates
  When  the handler processes the event
  Then  ALL active candidates are cancelled (existing behaviour: the loop over activeCandidates)
  And   each cancel uses the branch chosen by deactivationSource (uniform across all candidates)
LOGIC-4 (defensive): Missing or unrecognised cancel source → default to "cancelled upstream"
  Real-world: a guard. If CL ever emits without a source tag (bug, legacy producer,
  etc.), we must not silently attribute the cancel to the customer.

  Given a cancellation arrives with deactivationSource = null
        or an unrecognised string value
  When  the handler processes
  Then  the candidate routes to cancelByUpstream(...) (the safer default)
  And   the unrecognised value is logged at WARN for ops follow-up
  And   the candidate does NOT silently route to CANCELLED_BY_CUSTOMER
LOGIC-5: System-cancel → CleverTap event fires → CSP app removes the booking
  Real-world: when a system-side cancel reaches CANCELLED_BY_UPSTREAM, the CSP
  must see the booking disappear from their app. CleverTap is the notification channel
  the partner app subscribes to — it's what wakes the app and tells it to remove the task.

  Given the install candidate has landed in CANCELLED_BY_UPSTREAM
  When  the terminal transition completes
  Then  a CleverTap event fires carrying the cancelled bookingId / connectionId
  And   the CSP App consumes the CT event and removes the booking
        from its active-assignments list
  And   if the task was already open on the CSP's screen, it shows as cancelled

Use & edge cases

EDGE-1: Cancellation arrives but no install task exists for that connection
  Real-world: the install was never started, or it's already completed / cancelled.

  Given a cancellation arrives for a connection with no active install candidates
  When  the handler processes
  Then  no-op (existing behaviour: log + return)
  And   the deactivationSource branching does NOT trigger any state change
        (because there's nothing to cancel)
  And   no CleverTap event fires (nothing was active to remove)
EDGE-2: The same cancellation event is delivered twice (replay / retry)
  Real-world: message broker retries or replays. We must act on it only once.

  Given the same CL_DEACTIVATION_INITIATED is delivered twice
  When  the handler processes the duplicate
  Then  isDuplicate guard returns early on the second delivery
  And   no second cancel is triggered (existing idempotency)
  And   exactly one CleverTap event fires for the booking (not two)
EDGE-3: Historical cancellations (already in the database) are not re-classified
  Real-world: what was cancelled before this fix stays as-is. No retroactive change.

  Given the fix ships
  When  historical candidates (cancelled before this change) are queried
  Then  they continue to look like CANCELLED_BY_UPSTREAM with reasonCode = "DEACTIVATION"
  And   no retroactive re-classification happens
  And   no historical CleverTap event re-emits
EDGE-4: The split of cancellations changes from day zero — ops should expect it
  Real-world: the customer-cancel count rises from ~0 to its real value on day-zero.
  That's classification correctness, not a behaviour change.

  Given an internal dashboard that counted install cancellations by terminal
  When  this fix ships
  Then  the CANCELLED_BY_CUSTOMER count rises from ~0 to its real value
  And   the CANCELLED_BY_UPSTREAM count drops correspondingly
  And   ops should be told the swing is NOT a customer-behaviour change

Regression

REGRESSION-1 (A6 row 1): CL state-machine transitions for cancellation are untouched
  Real-world: the fix is on the receiving side (TAS). CL's own state changes
  must behave exactly as they do today.

  Given a customer cancel or system cancel via customer backend
  When  CL processes
  Then  T13 (PENDING_INSTALL → PENDING_DEACTIVATION) or T9 (REQUESTED → DEACTIVATED)
        fires exactly as today
REGRESSION-2 (A6 row 2): CSP-side cancel paths continue to land in CANCELLED_BY_UPSTREAM
  Real-world: things like CSP exit, D&A reallocation, Enforcement-driven termination
  don't go through CL_DEACTIVATION_INITIATED with USER_INITIATED at all, so they
  naturally stay in the upstream bucket.

  Given any non-CL_DEACTIVATION_INITIATED cancellation source (Exit, Enforcement,
        D&A REALLOCATION_PENDING, etc.)
  When  the cancel fires
  Then  it lands in CANCELLED_BY_UPSTREAM exactly as today
REGRESSION-3 (A6 row 3): Total cancellations per day stays identical pre vs post fix
  Real-world: bifurcation re-distributes between two buckets. It doesn't add or
  remove cancellations — the sum must match day-over-day.

  Given a 30-day window of install cancellations
  When  we count terminal-state cancellations per booking / CSP / zone
  Then  the count = (CANCELLED_BY_CUSTOMER + CANCELLED_BY_UPSTREAM)
        equals today's total cancellation count
REGRESSION-4 (A6 row 4): No copy or layout changes on either app
  Real-world: bifurcated data becomes available for future PN / UX work.
  This item ships no visual change to the apps.

  Given customer or partner app UI for cancellations
  When  this fix ships
  Then  no copy / layout / surface changes
REGRESSION-5 (A6 row 5): Duplicate cancellation events still cancel exactly once
  Real-world: the existing dedupe guard must continue to work.

  Given the same CL_DEACTIVATION_INITIATED is delivered twice
  When  both arrive at the install handler
  Then  exactly one terminal transition occurs (existing isDuplicate guard)
REGRESSION-6 (A6 row 6): Recharge TAS (the other consumer) is unchanged
  Real-world: recharge uses a different DTO that already handles the source-tag
  correctly. This fix is install-only.

  Given a CL_DEACTIVATION_INITIATED arrives at the recharge TAS handler
        (which uses a different DTO with 11 fields including deactivationSource)
  When  the recharge handler processes
  Then  behaviour is identical to today (the recharge DTO is not changed)
REGRESSION-7 (new): Customer-cancel → CleverTap event + CSP app removal still works
  Real-world: today the customer-cancel → CSP-app-removal chain works because every
  cancel routes through CANCELLED_BY_UPSTREAM. After this fix, customer-cancels route through
  CANCELLED_BY_CUSTOMER instead. The CT event and app removal must continue to fire from
  the new branch — no UX regression for the partner.

  Given a customer cancels (LOGIC-1 path) and the candidate lands in CANCELLED_BY_CUSTOMER
  When  the terminal transition completes
  Then  a CleverTap event fires for this candidate
  And   the CSP App removes the booking from its active-assignments list
        (unchanged user-facing behaviour from today)
