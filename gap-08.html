Wiom · Change Spec · v1.0 · PM deliverable · GAP-08

Customer-captured structured location + voice directions on the CSP / Technician app

Customer App now captures the install location as a structured object (house number, street, locality, landmark, pincode, city) plus a voice-recorded direction note uploaded to S3. None of this reaches the CSP / Technician App today — the partner sees only the customer's free-text address at booking, often inadequate (ambiguous landmarks, rural lanes without street names, multi-tenant buildings without floor markers). Voice directions are how the customer can explain "turn left after the white temple, the gate is opposite the chai shop" without typing it. Scope of this gap: backend-only. Get the structured-location object + voice-audio URL from Customer Backend into the CSP backend (TAS install-candidate), and expose both via the existing CSP-App-facing candidate-detail endpoint so the app can render them. Frontend rendering (audio player UI, address presentation) is a separate Surface Contract / app spec.

Author: Ashish Raj  ·  Reviewer: Customer Backend + TAS Engineering  ·  Tier: Light
Tier: Light — A1, A2, A5, A8, B5 + Workflow + Wired-layers. Backend-only spec: Customer Backend exposes the data, TAS persists it, CSP-app reads via existing candidate endpoint. Three connected changes: (1) Customer Backend pushes the structured-location + voice-audio fields to TAS at booking-creation time, (2) TAS persists both on the install_execution_candidate row, (3) TAS includes both in its CSP-facing candidate-detail response.
Rows: Required — every row filled or marked N/A with a reason.
Open items: TBC — exact field name + URL semantics (presigned vs durable) for the voice-audio link are pending Customer Backend team confirmation; placeholders used in §A5 and §B5 with explicit «TBC» markers.

Quick Check

7-line triage — read this before the rest.
What is changing?
Customer Backend → TAS pipeline for two payload additions: (1) customer_location_details — JSON object with the fields the Customer App captures today (home, streetNumber, locality, street, landMarkType, address, pincode, city); (2) voice_direction_url — S3 URL to the customer's voice-recorded address direction (field name «TBC by Customer Backend team»). Both flow into TAS via the existing ConnectionRequestCreated event payload (extended) and are persisted on install_execution_candidates. The existing CSP-facing candidate-detail endpoint returns both in its response so the CSP / Technician App can render them.
What triggered it?
Customer App rollout (2026 Q2) added structured-location capture + voice-direction recording at the BFP/booking-creation step. The fields land in Customer Backend at booking time and stay siloed there — TAS never receives them, CSP App never sees them. Field technicians have repeatedly flagged that the free-text address alone is insufficient for navigation in tier-2/3 cities and rural zones, where landmarks are spoken not written.
Blast radius
Customer Backend (booking service — payload extension on ConnectionRequestCreated) · TAS (inbound handler payload, candidate entity, DB migration for two new columns, candidate-detail response DTO) · CSP / Technician App (consumer of the candidate-detail endpoint — no code change in this spec, just consumes the new fields). No event-name change, no new event class, no schema break.
Who is affected?
Partners (CSP / Technician): get the structured address + audio cue at install time → fewer wrong-address visits, fewer customer call-outs. Customers: the voice they recorded actually reaches the technician — no silent loss of input. Ops: reduced "wrong address" install-failed reason codes, better first-visit success rate. Customer Backend team: must extend the existing event payload they emit today.
Spec source / inputs
Customer App captured shape (verbatim from PM observation): {"home":"R","streetNumber":"Test","locality":"Sector 32, 122001","street":"VE Commercial Vehicles Ltd.","landMarkType":"OTHER","address":"Ground Floor, Plot no. 94, Sector 32","pincode":"122001","city":"Gurugram"}. Voice URL field name: «TBC by Customer Backend team» — assumed key voice_direction_url for this spec, replace once confirmed.
Out of scope
CSP / Technician App UI for rendering the address layout (separate Surface Contract). Audio player controls (separate app spec). Voice transcription to text (future enhancement). Analytics on whether the audio actually got played (future). The customer-side capture flow itself — already live; this spec only consumes its output.
Hard checks (before sign-off)
Customer Backend team confirms the voice URL field name. URL semantics confirmed: is it a presigned URL with TTL, or a durable S3 path that TAS / CSP-app must combine with credentials? Auth for the audio fetch confirmed: does the CSP / Technician App fetch S3 directly with a presigned URL, or via a TAS pass-through endpoint? Existing ConnectionRequestCreated event subscribers (other than TAS) tolerate the payload extension (additive, not breaking).

A2. Why This Change WHAT

What is expected: The problem in plain English, who's affected, the cost of leaving it.
What's wrong with the current behaviour?Information asymmetry between booking-time and install-time. The Customer App now collects a structured address object (8 fields including landmark type, locality, street, pincode) AND lets the customer record a voice note explaining how to reach the install location. The structured object lands in Customer Backend; the audio gets uploaded to S3. None of this reaches TAS today — the install_execution_candidate row only carries the connection_id and customer_id. When the CSP / Technician App reads its candidate-detail endpoint, the technician sees only the free-text address string. Result: in zones where street names are absent (rural / interior), the technician arrives at the wrong place, calls the customer, sometimes fails the install entirely, and books a re-visit. The customer's voice explanation — recorded specifically for this moment — sits unheard in S3.
Who experiences it?Technicians / Partner field staff: first-visit success rate is lower than it should be in addressing-difficult zones; the input the customer provided was discarded by the pipeline. Customers: they spent the effort to record the voice note assuming it'd be heard — silent breakage of expectation. Ops: "wrong address" rejections show up as FAILED_AT_DOOR / NOT_FOUND patterns in install-failure analytics. Repeat-visit cost: each wrong-address visit consumes a slot, a router activation, and partner-payout dispute risk.
Cost of leaving it as-is?Every booking in an addressing-difficult zone has a structurally higher install-fail rate than it would with the structured fields + voice directions surfaced. The customer's voice note becomes a feature shipped on the Customer App that never closes the loop on the CSP side — a "shipped but inert" surface. As Customer App rolls structured-capture to more zones, the gap widens.
OS prescription (if any)None. This is operational data enrichment — no OS clause is being violated or restored. The data conceptually belongs to the customer's connection profile; carrying it forward to the install execution candidate is a UX completeness move, not a state-machine fix.

A5. The Delta WHAT

What is expected: One row per atomic change: what changes → before → after → why.
What changesBeforeAfterWhy
Customer Backend — extend ConnectionRequestCreated event payload with structured-location object The event carries connection_id, customer_id, zone_id, created_at, plus a free-text address string. The structured fields the Customer App captures (home, streetNumber, locality, street, landMarkType, address, pincode, city) live in Customer Backend's booking record but are not in the outbound event. Event payload gains customer_location_details — a JSON object with the eight fields the Customer App captures, passed through verbatim (no transformation, no field renaming). Sample shape: {"home":"R","streetNumber":"Test","locality":"Sector 32, 122001","street":"VE Commercial Vehicles Ltd.","landMarkType":"OTHER","address":"Ground Floor, Plot no. 94, Sector 32","pincode":"122001","city":"Gurugram"}. Field is optional at the schema level (older bookings without structured capture pass null); TAS gracefully handles absence. Carries the structured input from where it was captured (Customer App) to where it's needed (install execution). Verbatim pass-through avoids any semantic loss between capture and consumption. Schema-optional preserves backward compatibility for in-flight bookings created before this rollout.
Customer Backend — add voice_direction_url field to ConnectionRequestCreated payload TBC Voice-direction audio is uploaded to S3 by the Customer App at booking time. The S3 URL lives in Customer Backend's booking record but is not on the outbound event. Field name on Customer Backend's record is «TBC by Customer Backend team». Event payload gains voice_direction_url (string, optional). URL semantics are one of: (a) durable S3 URL (signed-on-fetch by the consumer), (b) presigned URL with TTL ≥ install window (P74 = 72h), or (c) opaque proxy URL served by Customer Backend with its own auth. Customer Backend team to confirm which. If presigned with shorter TTL than 72h, an additional fetch path is needed (see row 5). If field is absent (older bookings, or customer skipped voice recording), TAS persists null — not an error. Same pass-through principle as the location object — carry the captured signal to where it's consumed. URL semantics matter for the consumer (CSP App needs to know whether to fetch directly, refresh via TAS, or proxy through). Treating absence as valid means existing flows aren't blocked while structured capture is being rolled to more zones.
TAS — extend InboundEventProcessingService.process(ConnectionRequestCreated) to read the two new payload fields Handler reads connection_id, customer_id, zone_id, created_at and ignores everything else. No code paths today look at structured location or voice fields. Handler reads the two new fields. Both are nullable. Values are written through to the install_execution_candidate row at candidate-create time (which TAS already does on this event in some flows — confirm timing with TAS engineer; if not at this event, then at the AllocationAssigned moment when the candidate is actually created — see row 4 alternate). Single integration point for both fields; reuses the existing inbound event pipeline. No new TAS endpoint, no new event class. The location/voice are properties of the customer's booking, not of the CSP allocation — so they should land on TAS at the same moment the booking is acknowledged, not at allocation time.
TAS — add two columns to install_execution_candidates: customer_location_details (jsonb), voice_direction_url (text) Existing schema has execution_candidate_id, connection_id, csp_id, current_state, slot fields, deadline fields, reason fields. No customer-location field, no voice-direction field. Flyway migration adds two columns:
customer_location_details JSONB NULL — stores the verbatim object from the event payload.
voice_direction_url TEXT NULL — stores the URL from the event payload. No index needed (read-only on candidate-fetch by id; not queried by location content).		 JSONB for the structured location is correct (schema may evolve with new keys; treating as opaque JSON avoids per-field migrations downstream). Text for the URL is sufficient. NULL allowed because: (a) older bookings predate structured capture, (b) the customer can skip voice recording, (c) URL semantics may need a fetch-time refresh (see row 5).
TAS — extend the CSP-facing candidate-detail response DTO with the two new fields The existing CSP-facing endpoint (GET /candidates/{candidate_id} or the /home/feed aggregation endpoint — confirm exact endpoint name with TAS engineer) returns slot timing, customer name/contact, address text, and state. No structured location, no voice URL. Response DTO gains:
customer_location_details — the JSON object from the candidate row, passed through as-is.
voice_direction_url — the URL from the candidate row. If Customer Backend uses presigned-with-short-TTL semantics (row 2 option b), TAS calls a Customer Backend refresh-URL endpoint at response-build time and returns a freshly-signed URL. Otherwise TAS returns the stored URL verbatim. Authorization unchanged — existing CSP-auth check on candidate-detail endpoint ensures only the assigned CSP sees the data.		 The CSP App already polls / fetches candidate detail to render the booking. Extending that response is the smallest CSP-app surface change (just consume two new optional fields). No new endpoint, no new auth model. Putting the URL-refresh on the read path rather than write path means stale-URL handling lives in one place, deterministically.
CSP / Technician App — consume the two new response fields consumer awareness only App renders the free-text address string from the candidate-detail response. App reads the two new fields when present, renders the structured address layout above the free-text fallback, and exposes the audio via a player control. UI rendering details are out of scope for this spec (separate Surface Contract) — this row exists to confirm the consumer is informed that the contract is extending. Closes the loop. Without the consumer consuming, the backend changes are inert. The Surface Contract spec will detail the layout, audio player, fallback behaviour, accessibility.
Why an event-extension and not a new event. The customer's structured location and voice direction are properties of the existing ConnectionRequestCreated domain fact — a booking was created with these inputs. They should live on the same event, not in a sibling "BookingDetailsAdded" event that would require ordering guarantees between the two. Additive payload extension is backward-compatible (older consumers ignore unknown fields) and atomic with the booking creation.
TBC for Customer Backend team: (1) Confirm the exact field name for the voice S3 URL on the booking record. (2) Confirm URL semantics — durable S3 URL, presigned with TTL (and what TTL), or proxy URL via Customer Backend. (3) If presigned with TTL < P74 (72h), confirm whether Customer Backend exposes a refresh endpoint TAS can call at candidate-detail-fetch time. (4) Confirm whether all existing ConnectionRequestCreated consumers tolerate the additive payload (forward-compatible deserialization).

B5. Acceptance Criteria — Verification Layer HOW

What is expected: Given / When / Then blocks covering the data-flow contract. §A6 + REGRESSION omitted per gap-05 v1.2 PM convention.

Business logic

LOGIC-1: Happy path — booking with all fields → TAS persists → CSP-App reads
Real-world: normal booking in a zone where Customer App captures structured location AND the customer recorded a voice note.

Given a Customer App booking with the full location object captured
      AND a voice direction uploaded to S3 with URL <voice_url>
When  Customer Backend emits ConnectionRequestCreated for <connection_id>
Then  the event payload contains both:
      customer_location_details = {home, streetNumber, locality, street, landMarkType, address, pincode, city}
      voice_direction_url = <voice_url>
And   TAS handler writes both fields to install_execution_candidates row for <connection_id>
And   GET /candidates/{candidate_id} returns both fields in the response

Verify:
  • TAS DB — install_execution_candidates
      WHERE connection_id = <connection_id>
      → customer_location_details (jsonb) matches the captured object byte-for-byte
      → voice_direction_url = <voice_url> (or refreshed equivalent if presigned)
  • TAS response — candidate-detail endpoint includes both fields
  • Customer Backend event log — ConnectionRequestCreated payload carries both fields
LOGIC-2: Customer skipped voice recording (structured location only)
Real-world: common case — customer fills the address fields but doesn't record voice.

Given a Customer App booking with the location object captured
      AND no voice recording
When  Customer Backend emits ConnectionRequestCreated for <connection_id>
Then  the event payload contains:
      customer_location_details = {...8 fields...}
      voice_direction_url = null (or field absent)
And   TAS handler writes location_details, writes NULL for voice URL
And   GET /candidates/{candidate_id} returns location_details object, voice_direction_url = null

Verify:
  • TAS DB — voice_direction_url IS NULL on this row
  • TAS response — voice_direction_url field present in JSON with value null
  • CSP App is expected to gracefully hide the audio player when null (out of scope for this spec)
LOGIC-3: Older booking predating Customer App structured capture
Real-world: in-flight bookings that were created before Customer App rolled out the structured capture flow. Backward-compat case.

Given a Customer App booking from before the structured-capture rollout
      AND only the free-text address string is on the booking record
When  Customer Backend emits ConnectionRequestCreated for <connection_id>
Then  the event payload may have:
      customer_location_details = null (or field absent)
      voice_direction_url = null (or field absent)
And   TAS handler writes NULL for both
And   GET /candidates/{candidate_id} returns both as null
And   the existing free-text address field on the response is unchanged

Verify:
  • TAS DB — both new columns IS NULL on this row
  • TAS response — both fields present with value null
  • Negative — no error, no warning, no fallback hardcoding (genuine null, not empty object)
  • Existing flows for this connection (slot proposal, install, etc.) work unchanged
LOGIC-4: URL refresh path (conditional — only if presigned with TTL < 72h)
Real-world: if Customer Backend uses presigned URLs with TTL shorter than P74, TAS must refresh the URL when the CSP App requests candidate detail.

Given voice_direction_url stored on install_execution_candidates was issued T-hours ago
      AND Customer Backend's presigned TTL is < 72h (e.g. 24h)
      AND T >= (TTL - safety_window)
When  CSP App calls GET /candidates/{candidate_id}
Then  TAS detects the stored URL is near-expiry
And   TAS calls Customer Backend's refresh-URL endpoint for <connection_id>
And   Customer Backend returns a fresh presigned URL
And   TAS returns the fresh URL in the response (does NOT need to persist it; can re-refresh on next call)

Verify:
  • TAS response — voice_direction_url field carries a fresh signature timestamp
  • TAS logs — URL-refresh call to Customer Backend recorded
  • Customer Backend logs — refresh endpoint hit
  • If URL semantics are durable (option a) or TTL ≥ 72h, this LOGIC is N/A — no refresh path exists

Use & edge cases

EDGE-1: Customer Backend refresh endpoint unavailable (degraded)
Real-world: only applies if LOGIC-4's refresh path is wired. Customer Backend returns 5xx or times out.

Given the URL refresh path is wired (LOGIC-4)
      AND Customer Backend's refresh endpoint returns 503 or times out
When  CSP App calls GET /candidates/{candidate_id}
Then  TAS logs the failure with WARN
And   TAS returns the candidate-detail response WITHOUT failing — voice_direction_url field is null
      OR returns the stored (possibly expired) URL with a flag indicating "may be stale"
        (PM decision — leaning toward null with WARN)
And   the rest of the response (location_details, slot, state) is unaffected

Verify:
  • Service logs — WARN entry for the refresh failure on this candidate
  • TAS response — voice_direction_url = null (decision: null is safer than stale)
  • Negative — request does NOT fail; CSP App still gets the candidate detail
EDGE-2: S3 audio object missing / deleted
Real-world: retention policy removed the audio, or it was manually deleted by ops. URL exists but fetch returns 404.

Given voice_direction_url is set on the candidate row
      AND the underlying S3 object is no longer present
When  CSP App resolves the URL and fetches the audio
Then  S3 returns 404
And   CSP App handles the 404 gracefully (UI behaviour — out of scope here)
And   TAS is not involved in this failure path — no log on TAS side
And   Future candidate-detail responses still carry the URL (TAS does not detect S3-side absence)

Verify:
  • Documented expectation — TAS does NOT verify S3 object presence
  • If retention removal is a real concern, Customer Backend should null the URL on its side
    when the object is purged; that null propagates on the next ConnectionRequestCreated
    or via an explicit BookingUpdated event (future enhancement, out of scope)
EDGE-3: Customer App captured a partial structured object
Real-world: customer filled some fields, skipped others. Customer App allows partial submission.

Given the Customer App submission had only home, address, pincode, city
      AND streetNumber, locality, street, landMarkType are empty / null
When  Customer Backend emits ConnectionRequestCreated
Then  the event payload's customer_location_details object preserves the partial shape
      (missing keys, or keys present with null values — Customer Backend chooses)
And   TAS persists the object verbatim
And   GET /candidates/{candidate_id} returns the object verbatim

Verify:
  • No validation enforcement on the structured object's internal shape — TAS treats it
    as opaque JSON. Validation of which fields are mandatory lives on the Customer App
    submission flow, not on TAS.
  • CSP App rendering handles missing keys gracefully (out of scope here)
EDGE-4: Event payload extension breaks existing consumer
Real-world: some other service subscribes to ConnectionRequestCreated and its deserializer is strict
about unknown fields. Should never happen with well-behaved services but worth verifying.

Given the existing ConnectionRequestCreated has consumers other than TAS
      (CL, Capacity OS signals, analytics, etc.)
When  the extended payload (with the two new fields) is published
Then  all existing consumers continue to process events successfully
And   no consumer fails with "unknown field" deserialization error

Verify:
  • Integration test in staging: publish an extended-payload ConnectionRequestCreated,
    confirm every subscriber processes it without error
  • Service logs across all subscribers — no deserialization warnings
  • If any consumer is strict-mode, coordinate the schema update with that team
    (this is why §A8 has an ESR row)
