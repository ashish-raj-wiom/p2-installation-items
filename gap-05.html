Wiom · Change Spec · v1.2 · PM deliverable · GAP-05

Prevent re-allocation to same CSP after install failure

Once a CSP marks INSTALLATION_FAILED for a connection, they must never receive that same connection again. Today they can — in single-CSP zones the routing engine's SINGLE_CSP_ZONE_CONTINUITY bypass re-includes the cooled-down CSP for the same connection, and the install-failure handler doesn't increment the per-CSP P195 ping-pong counter so the lifetime cap never fires for this path. Three coordinated changes: increment P195 on install-failure, remove the single-CSP bypass, set P195 = 1 globally. v1.1 — corrected every Verify block against the actual DAS schema (table is allocation_audit_log, exclusion-reason enum is P195_PING_PONG, bypass column is cooldown_bypassed_for_continuity); restated §A8 per the OS Governance Reference (zero OS amendments — see §A8); flagged a P51 code/OS drift surfaced during audit.

Author: Ashish Raj  ·  Reviewer: Engineering  ·  Tier: Light
Tier: Light — A1, A2, A5, A8, B5. Three-file change (two .java + one config). Per OS Governance Reference: zero OS amendments, one parameter change, two execution fixes. v1.2 — §A6 and B5 REGRESSION blocks removed by PM decision; B5 scope is LOGIC + EDGE only.
Rows: Required — every row filled or marked N/A with a reason.

What is changing?
The DAS install-failure handler now increments the per-CSP P195 counter alongside the existing P51 cooldown. The single-CSP fallback bypass in RoutingEngineServiceImpl is removed. The P195 default goes from 3 (code) / 2 (OS) to 1. Combined effect: once a CSP marks install-failure for a connection, that connection never goes back to them — multi-CSP zone reroutes, single-CSP zone produces a service vacuum until the existing CL P75 sweep deactivates it.
What triggered it?
Live QA verification — across 8 recent install-failure → CL retry cycles, every assignment_count_per_csp was empty {}. The counter the OS-mandated P195 cap depends on never increments on the install-failure path. Compounded by the single-CSP fallback which re-includes the P51-cooled CSP for "continuity over starvation."
Blast radius
DAS only. InboundEventProcessingServiceImpl.java (one line added in install-failure handler) · RoutingEngineServiceImpl.java (single-CSP fallback block removed) · DemandAllocationParameters.java + application*.yml (P195 default 3 → 1). D&A OS: §P195 default + FM-DAO-12 wording.
Reversible?
Yes — config-level rollback of P195; code revert of the two file edits.
Money / PII / migration?
No / No / No. Going-forward only — no backfill of historical connections.
OS impact / sign-off?
Per OS Governance Reference Q1–Q3 routing: zero OS amendments. The bypass is NOT in the D&A OS (it violates INV-DAO-02 "no bypass path"); removing it is code-OS realignment. The install-failure increment is also realignment (FM-DAO-12 names "decline or fail"). P195 = 1 is a calibration parameter change within the existing @Min(1) range. One parameter change (P195), two execution fixes. Sign-off Pending (D&A OS owner).

A2. Why This Change WHAT

What is expected: A short problem statement. Observable trigger, who is affected, cost of leaving it.
All rows required
QuestionAnswer
What's wrong with the current behaviour?Three-part defect that compounds. (1) The DAS install-failure handler at InboundEventProcessingServiceImpl.java:451-454 calls addDeclineCooldown(...) (writes the 24h P51 cooldown) but does not call incrementAssignmentCount(...) — so the per-CSP P195 counter never moves on install failure. (2) RoutingEngineServiceImpl.java:108-135 ("v1.5: Single-CSP fallback — continuity over starvation") re-includes a P51-cooled CSP into the eligible pool whenever the entire exclusion set is "P51-only" and the bypassed CSP is the only candidate in the zone. (3) The P195 default is 3 in code (DemandAllocationParameters.java:98-100) and 2 in OS (L572) — neither matches the "one CSP, one attempt" policy this gap establishes. Combined effect: a CSP marks install-failure → 24h P51 cooldown fires → in a multi-CSP zone P51 alone is enough to reroute, but in a single-CSP zone the bypass re-includes the same CSP and the connection goes back to them. Even after 24h, no P195 increment means the CSP is eligible again for any reason at all.
Who experiences it?Customer — gets a technician dispatched from the same CSP that just marked their install failed. CSP — gets a booking back they already declined for fundamental reasons (coverage, backhaul, device). Wiom — wasted re-allocation; the install-failure signal carries no operational weight. Re-verified in QA (v1.1): last 6 install-failure → CL_RETRY_REROUTE rows in public.connection_allocations all show previous_csp_id = a0a0m0, decline_cooldown_csp_ids = [{cspId: "a0a0m0", ...}] (P51 fires), and assignment_count_per_csp = {} (P195 counter never moves). The trigger source IS being captured today — allocation_audit_log.cooldown_trigger_source = 'INSTALL_FAILURE', cooldown_target_csp_id = a0a0m0. Only the counter increment is missing.
Cost of leaving it as-is?Every install-failure in a single-CSP zone today loops back to the same CSP. The defect cannot be fixed by config tuning alone (P195 lower bound has no effect when the counter never increments). It compounds with the broken P41 timeout sweep (BUG-02) — when the scheduler is restored, P41 timeout-driven retries would also start landing back on the same CSP unless this gap is closed first.

 Block removed entirely (along with the cooldownBypassed / cooldownBypassReason variables that feed only the audit log). When the eligible pool is empty, the routing pass returns ALLOC_STATE_ROUTING_FAILURE with LOOP_EXHAUSTED as today. The three scenarios the bypass protects all collapse: P41 timeout isn't wired in prod (BUG-02 — scheduler down); decline is rare and per stated policy a declined-then-resent booking is not desired anyway; install-failure is the bug. Keeping the bypass forces us to rely on implicit "bypass only fires for P51-only exclusions" behaviour — fragile to refactor.
P195 default value — DemandAllocationParameters.java:98-100 + application*.yml Code default = 3; OS default = 2: 
@Min(1) @Max(10)
private int p195SameConnectionReassignLimit
    = 3;
 Code default = 1; OS default = 1: 
@Min(1) @Max(10)
private int p195SameConnectionReassignLimit
    = 1;
 One CSP, one attempt per connection — the policy this gap establishes. Applies uniformly across all three trigger paths (decline / P41 timeout / install-failure). Each path already increments the counter (or will, after the change above), so all three reach the cap on first attempt and the CSP is permanently excluded from that connection.
D&A OS — §P195 default + FM-DAO-12 wording §P195: default = 2. FM-DAO-12 framed around "ping-pong tolerance" between CSPs in a multi-CSP zone. §P195: default = 1. FM-DAO-12 wording amended: "one CSP, one attempt per connection — once any of decline / acceptance-timeout / install-failure fires, that CSP is excluded from this connection's lifetime." Aligns OS text with the new operational policy + the code change. Recipients (Tech, Quality OS) read OS not code.
What does not change: The P51 cooldown duration (parameter p51DeclineCooldownHours at DemandAllocationParameters.java:68; currently 4h in code, 24h per D&A OS L566 — a drift this gap does not touch) stays exactly as-is. P51 continues to fire as today on all three trigger paths. The change is additive: P195 also fires now on the install-failure path. After the fix, install-failure on a CSP results in both a P51 exclusion (time-bounded) and a P195 exclusion (permanent, lifetime of the connection). The permanent one is what matters once the P51 window elapses; the P51 one matters during the immediate retry window.
Service-vacuum behaviour: In a single-CSP zone, after install-failure the routing engine emits ALLOC_STATE_ROUTING_FAILURE with LOOP_EXHAUSTED. The connection stays in CL REQUESTED. The existing CL P75 sweep (7-day expiry) eventually transitions it to DEACTIVATED. If the customer wants service, they rebook — a new connection_id is created, P195 counters start fresh, and the previously-failed CSP is eligible again on the new connection. This is the OS-sanctioned recovery path; no new notification surface ships in this gap.
