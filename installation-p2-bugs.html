BUG-01

CLOS timeout scheduler unwired (P75 / P76 / P77 inert)

CL OS defines four system-driven timeouts that must fire on background sweeps. The batch methods, endpoints, and scheduler hooks all exist in code — but the AWS EventBridge scheduler is disabled in prod (AWS_SCHEDULER_ENABLED: false) and nothing calls scheduleRecurring(...). Zero system-driven CL transitions in 90 days. P74 is out of scope for this item — its start-time anchor is a separate PM decision.

DAS scheduler unwired (P191 held-allocation reroute inert)

Same scheduler-wiring failure as BUG-01, this time on DAS. P191's held-allocation reroute sweep is supposed to retry UNASSIGNED allocations periodically; instead 230 rows sit untouched. P41 (acceptance window) is out of scope for this item — its start-time anchor is a separate PM decision.

BUG-03

DAS allocation state never reaches ACCEPTED (DAS-internal atomic write required)

AMENDMENT-02 (Apr 2026) deleted the explicit CSP-accept call and declared acceptance "automatic on assignment". DAS has the receiver fully wired (POST /api/demand-allocation/csps/{cspId}/accept + AllocationServiceImpl.acceptAllocation(...)); no service calls it. Result in prod: 0 rows ever in ACCEPTED; 504 / 504 stuck at ASSIGNED / UNASSIGNED; acceptance_timestamp NULL on every row.

BUG-04

DAS skips active-connection increment — P46 routing enforcement effectively disabled

DAS routing's per-CSP-per-zone P46 cap guard (AllocationGuards.guardCspBelowP46Cap) reads CspZoneExposureEntity.activeConnections — but this counter is only ever decremented, never incremented in DAS code. The counter stays clamped at 0 → the guard if (activeConnections >= p46CapacityCap) never trips → P46 cap enforcement at routing time is effectively disabled. DAS will allocate to a CSP regardless of their actual active load. Real-time, every allocation, every zone. Not CSP-app-visible — partner app reads CL directly.

BUG-05

CL_INSTALLATION_QUALITY_SIGNAL — producer-record contract drifted from CL OS §S-10

CL emits the signal on every T2; Quality OS rejects every single one with HTTP 400 VALIDATION_FAILED. 53 emissions, 0 delivered, 100 % failure rate. Root cause: payload-contract drift in the CL producer record. Three required fields don't match the CL OS S-10 + base-schema contract.

CL_CONNECTION_ACTIVATED doesn't carry customer_id in its payload, so the CAEO consumer plugs cspId in as a placeholder. Want: customer_id gets populated in the CL event so that CAEO's customer_id column carries the actual customer.
